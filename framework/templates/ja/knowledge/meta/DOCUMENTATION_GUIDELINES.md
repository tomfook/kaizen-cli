# ドキュメントガイドライン

`knowledge/`ファイルおよびプロジェクト固有ドキュメント（`docs/`、`CLAUDE.md`）の品質維持ガイドライン。

**重要**: プロジェクト横断ファイルのみ。プロジェクト固有の内容を追加しないこと。

---

## ファイルサイズ管理

`knowledge/`のファイルは約800行以内に収める。

**理由**: Claude Codeのコンテキストウィンドウの効率的利用、高速アクセス、保守性の確保。

**基準**:
- 1ファイル: 最大800行
- 注意サイン: 600行超で改善を検討
- 改善の優先順位: **第1: 内容の精査・削減** → **第2: ファイル分割**

### 内容の精査

**削除前の転記確認（最優先ルール）**

1. 削除する情報が他のファイルに配置すべきものか判断する
2. 転記先に同等の情報が既に存在するか確認する
3. 転記が必要な場合、**必ず転記してから削除**する
4. 情報損失の防止が最優先

**禁止**: 転記確認なしの情報削除。

### 精査の基準

1. **重複の除去**: ファイル間で同一情報がないか確認、類似手順はマージ
2. **冗長な例の削減**: 例は1-2個まで、コマンド実行で確認できる出力は省略
3. **長いスクリプトの簡潔化**: 25行超のスクリプトはポイントのみに凝縮
4. **セクションのマージ**: 類似セクションを統合、曖昧な境界を整理
5. **情報の階層化**: 頻繁な操作は詳細に、まれな操作は概要のみ

### 行数削減の優先順位

1. **最優先**: 正確性と網羅性（必要な情報は絶対に削除しない）
2. **第2優先**: ドキュメントの使いやすさ
3. **第3優先**: 行数の削減

**判断テスト**: 「この情報を削除したら、開発者が困るか？」

### 分割の方針

内容精査後も600行超の場合にのみ分割を検討:
- トピックごとに独立したファイルに分離
- INDEX.mdで全体構造をナビゲート
- 関連ファイル間を相互参照リンクで接続

## INDEX.md 設計ガイドライン

`knowledge/`の各サブディレクトリには、**タスクディスパッチャー**としてのINDEX.mdを配置する。

### INDEX.mdの役割

INDEX.mdは「タスク別の逆引きリファレンス」— **Claude Codeが最初に読むべきファイル**。

**目的**:
- 「やりたいこと」から「どのファイル/セクションを読むべきか」に即座にナビゲート
- 1ファイルを読むだけで関連情報の所在を把握
- コンテキストウィンドウの効率的利用

**INDEX.mdに含めるもの**:
1. **Find by Task**（必須）: タスク別の逆引きテーブル
2. **File List**（必須）: 各ファイルの概要と行数
3. **Related Guides**（必須）: 他ディレクトリへのリンク

**INDEX.mdに含めないもの**:
- 詳細な内容説明（各ファイルの先頭に記載する）
- 学習パスや推奨読み順
- 対象読者や前提条件

### 標準INDEX.md構造

```markdown
# [Directory Name] - Reverse Lookup Reference

[One-line description]

**Important**: Cross-project files only. Do not add project-specific content.

## Find by Task

| What you want to do | Reference |
|---------------------|-----------|
| [Specific task] | [Filename § Section](./filename.md#anchor) |

## File List

| File | Description | Lines |
|------|-------------|-------|
| [Filename](./filename.md) | [One-line description] | ~XXX |

## Related Guides

- **[Category]**: [Link](./path) - [One-line description]
```

### INDEX.md 設計チェックリスト

- [ ] 「Find by Task」テーブルがあるか？
- [ ] 各エントリが特定のセクションにリンクしているか？
- [ ] File Listに行数が含まれているか？
- [ ] Related Guidesへのリンクがあるか？
- [ ] INDEX.mdは100行以内か？

## Single Source of Truth（SSOT）

各トピックの詳細説明は1箇所にのみ存在すべき。他のファイルはそこにリンクする。

**原則**:
- 同じ情報を複数ファイルに書かない
- 詳細説明は権威あるファイルに集約
- 他ファイルにはポイントのみ記載し、権威ソースにリンク

### 参照フォーマット

**knowledge/内のファイル間**:
```markdown
> 詳細: [ファイル名 § セクション](./filename.md#anchor)
```

**skillファイル（.claude/skills/）からknowledge/への参照**:
```markdown
> 詳細: `knowledge/path/to/FILE.md` § セクション名
```

**理由**: 相対パス（`../../../`）はシンボリックリンク環境で壊れる可能性がある。プロジェクトルート相対パスを使用する。

## ドキュメント品質

### 削除前の参照チェック

ドキュメントの削除・移行前に、他ファイルからの参照を検索:

```bash
grep -r "FILENAME.md" knowledge/
```

### 品質チェックリスト

`knowledge/`ファイルの編集・追加時:

- [ ] **SSOT**: 同じ情報がファイル間で重複していないか？
- [ ] **参照**: 参照は標準フォーマットを使用しているか？
- [ ] **参照先**: 参照されたセクションが実際に存在するか？

## プロジェクト固有ドキュメント（docs/、CLAUDE.md）

`knowledge/`はプロジェクト横断ファイル。プロジェクト固有情報は`docs/`と`CLAUDE.md`に配置。

### ファイル配置

| 配置場所 | 内容 | 用途 |
|---------|------|------|
| **knowledge/** | プロジェクト横断の知識 | 全プロジェクトで共有 |
| **CLAUDE.md** | プロジェクト固有の重要情報 | 用語、データソース、成果物 |
| **docs/** | プロジェクト固有の詳細情報 | 計画、意思決定ログ、仕様書 |

### CLAUDE.mdのサイズルール

| 閾値 | アクション |
|------|----------|
| **200行未満** | 正常 |
| **200-300行** | 詳細をdocs/に移動することを検討 |
| **300行超** | 詳細をdocs/に移動必須。CLAUDE.mdは参照のみに |

### Document Role Boundaries

プロジェクト固有の `docs/` ファイルは役割が重ならないよう分担する。各事実は1ファイルにのみ置く（SSOT）:

| ファイル | 役割 | 答える問い |
|---------|------|-----------|
| `docs/NEXT_STEPS.md` | これからやる作業・先送り | 「次に何をやるか / 何を先送りしたか」 |
| `docs/PROJECT_SUMMARY.md` § Design Decisions | 意思決定の記録（ADR的） | 「なぜそう決めたか」 |
| `docs/LEARNINGS.md` | 失敗・制約・落とし穴 | 「何が失敗したか / 何を避けるか」 |

**`docs/NEXT_STEPS.md`** は任意であり **必要時に作成**する（`init` ではスキャフォールドしない）。2節構成: `## Open items`（着手予定だが未着手の実行可能項目＋状態）と `## Deferred`（先送り項目＋理由・条件・日付）。短く保ち、完了・不要項目は `/kaizen-update-docs` で剪定する。維持されない NEXT_STEPS は無い方がマシ。

## Auto Memory（~/.claude/projects/）の位置づけ

Claude Codeのauto memory機能は、AIが会話間で学習を蓄積するローカルストレージである。

### memoryの特性

| 特性 | 意味 |
|------|------|
| **プロジェクト単位** | working directoryごとに分離される |
| **git管理外** | 履歴・差分・レビューがない |
| **マシンローカル** | 環境移行で消失する |
| **AI専用** | 人間が日常的に閲覧・管理しない |

### ドキュメント vs memoryの判断基準

情報を記録する際、以下の**いずれか1つでも該当すれば**ドキュメント（docs/、CLAUDE.md、knowledge/）に記載する：

| 判断基準 | 該当すればドキュメント |
|---------|---------------------|
| **復元コスト** | 失われたら再構築に手間がかかる |
| **読者の存在** | チームメンバーや未来の自分が参照する可能性がある |
| **意思決定の根拠** | 「なぜそうしたか」の追跡が必要 |

**すべてに非該当**の場合のみ、memoryに記録してよい。memoryには特に短期的・一時的な情報が適する。

### 具体的な配置先

| 情報の例 | 配置先 | 理由 |
|---------|--------|------|
| 「テストはpytestで回すこと」 | CLAUDE.md | チームルール、失われると困る |
| 「このアプローチが効果的だった理由はX」 | docs/ | 運用知見、意思決定の根拠 |
| 「この設計にした理由はXだから」 | docs/ | 意思決定の根拠 |
| 「説明は簡潔にして」 | memory | 個人の好み、また言えばいい |
| 「今週はリリースフリーズ」 | memory | 一時的、来週には無意味 |
| 「私はデータサイエンティストです」 | memory | 個人プロファイル |

### memoryからドキュメントへの昇格

memoryは低コストな記録手段として活用し、価値が確認できた時点でドキュメントに昇格する。

**昇格のシグナル**:
- 複数セッションにまたがって繰り返し参照している
- 他のドキュメントやルールと関連づけて運用している
- 「これが消えたら困る」と感じた

**昇格先の判断**:
- プロジェクト固有の知見 → docs/LEARNINGS.md、CLAUDE.md
- プロジェクト横断の知見 → knowledge/の該当ファイル

**昇格時の作業**: ドキュメントに転記した後、元のmemoryファイルとMEMORY.mdのエントリを削除する（SSOT維持）。

### Claudeへの指示

- memoryへの書き込み時は上記の判断基準に従い、**ドキュメントに該当する情報をmemoryに書き込まない**こと
- ドキュメントに該当する場合は、memoryではなくドキュメントへの追記を提案すること
- memoryに記録した情報が昇格シグナルに該当すると気づいた場合は、ドキュメントへの昇格を提案すること

## バックアップファイル管理

**重要**: バックアップファイル（`*.backup`、`*.tmp`等）を`knowledge/`ディレクトリ内に作成しないこと。

**理由**: `knowledge/`は共有リポジトリへのシンボリックリンク。バックアップファイルの作成は全プロジェクトに影響する。

**正しい方法**: プロジェクトローカルの`backups/`ディレクトリに配置する。

## 教訓昇格マーカー

`docs/LEARNINGS.md` のプロジェクト固有教訓を `knowledge/` 配下のクロスプロジェクトファイルに昇格させた場合、元のエントリに「昇格先マーカー」を付ける。`/kaizen-audit-knowledge` のクロスプロジェクト監査（`kaizen-learning-auditor`）がカバー済みと判定して再提案をスキップする。

**構文**:

```markdown
- **昇格先**: → knowledge/<path>.md § <セクション名>
```

**配置**: エントリ末尾の bullet として、`- **教訓**:` の後に追加する。

**例**:

```markdown
### S3 prefix listing pitfall (2026-05-10)

- **状況**: 分析プレフィックスの一括 listing
- **問題**: List API が継続トークンなしで部分結果を返した
- **教訓**: `ContinuationToken` で必ずページングする
- **昇格先**: → knowledge/aws/s3.md § Prefix listing semantics
```

**理由**: auditor はこのマーカーを検出して昇格候補ランキングから除外する一方、Step 3 のクロスプロジェクトパターン検出ではキーワードとして引き続き利用する。マーカーがないと同じ教訓が監査のたびに新規候補として浮上し続ける。

**複数マーカー**: 1 エントリが複数の knowledge ファイルに分割昇格された場合、`- **昇格先**:` 行を複数並べてよい。それぞれをカバー先として扱う。

# kaizen-reflect-learning

現在のClaude Codeコンテキスト（今日のいままでの作業履歴）から得られた知見を分析し、
プロジェクト横断のknowledge/ファイルに**簡潔に**反映する。

**言語**: ユーザーの言語に合わせて応答すること

**サブエージェント委譲**: 調査フェーズを `kaizen-learning-reflector` に、独立検証を `kaizen-learning-verifier` に委譲する。会話履歴を参照できるのはメインエージェントだけなので、事実ペイロードの構成はメインの責務。情報分離（reflectorの推論過程をverifierに渡さない）もメインエージェントの責務。

## このSkillの範囲

- **含まれる情報**: 反映フロー（事前準備〜Step 9、メインエージェント専用）
- **含まれない情報**: 判定基準（何を残すか・抽出カテゴリ・データ主張の粒度分離・ファイル反映のルール・knowledge/ の検索方法・簡潔性の原則）は [CRITERIA.md](CRITERIA.md) に分離
- **サブエージェント 2 体は CRITERIA.md だけを読む**。本ファイルは読ませない（毎回の読込コストを抑え、verifier が代替先推奨マトリクスやメインの手順を読んで判定を寄せることを防ぐ）。spawn プロンプトに本ファイルの内容やパスを書かない

## 反映フロー

### 事前準備（Step 1 の前に必ず実施）

reflector / verifier が分析できるのは **spawn プロンプトで渡された事実のみ**（サブエージェントは親セッションの会話履歴を見られない）。**ペイロードに含めなかった事実は、reflector・verifier のどちらからも観測できず、後段で回収不能**になる（verifier にも同じペイロードの原文を渡すため → Step 2）。メインエージェントは会話履歴から下記「必須ペイロード（5項目）」を漏れなく列挙してから reflector を spawn すること（**列挙完了後に spawn、reflector spawn と並行させない**）。

#### 必須ペイロード（5項目）

1. **失敗・リトライ・方針転換の全列挙**: エラー発生→修正して再実行、やり直し、アプローチ転換（カテゴリ1/3/7の素材）
2. **ユーザー修正指示・指摘の全列挙**: 修正依頼、方向転換の指示、追加要求（カテゴリ2/7の素材）
3. **外部調査の全列挙**: WebFetch / WebSearch / MCP（`mcp__context7__*`、`mcp__aws-documentation-mcp-server__*` 等）で調査した内容と得られた知識。長いセッションでは外部調査が埋もれやすいため、使用ツールを先に列挙してから内容を書く（カテゴリ9の素材）
4. **参照した knowledge/・Skill とその過不足**: セッション中に参照した横断ファイルと、説明不足・不正確・手順欠落・見つけにくさがあった箇所（カテゴリ4/8の素材）
5. **新規に扱った技術・ツール・サービス・横断パターン**: 概要と参照先（カテゴリ5/6の素材）

該当が無い項目は「なし」と明記する（暗黙の省略はペイロード欠落と区別できない）。

ペイロードは 1 つのテキストとして書き、手元に残す。Step 1 と Step 3 で**同じ原文**を渡す。

#### 反映前の実態確認

セッション中に「ファイル / symlink / 環境変数 / 設定が◯◯の状態である」という事実主張があった場合、推測のまま渡さず `ls -la` / `readlink -f` / `printenv` 等で現物確認してからペイロードに書く。他端末ブランチのマージレビュー時にも同じ実態確認を行うこと（追加された path/symlink/環境依存記述が自端末で成立するか確認）。

#### データ主張の粒度分離

数値比較・クエリ結果差異・集計値の不一致を根拠とする事実を書くときは、`.claude/skills/kaizen-reflect-learning/CRITERIA.md § データ主張を含む知見の粒度分離` に従い、Raw measurements（生観測）と Derived claims（派生主張）を分けて書く。派生主張は、反対方向の検証を1つ以上実施し、その結果（コマンドと出力）を添えてから渡す。検証していない派生主張を渡すなら「未検証」と明記する（事実として渡すと、verifier はそれを前提に判定するため独立検証が成立しない）。

**因果の主張と数も、同じ節に従う**:

- 「X を変えたら直った」と書くのは、X だけを変えた再現を 1 回通したあとに限る。通していなければ、症状と、変えたものすべて（差分）を書き、原因は書かない。複数の変更を同時に入れて直った場合、どれが効いたかは「直った」という事実からは分からない
- 回数・時間・件数は記憶で書かない。数え直すか、数えていなければ「未計数」と書く

### Step 1: kaizen-learning-reflector 呼び出し

Agent ツールで `kaizen-learning-reflector` を呼び出し、分析結果を取得する。
プロンプトには「事実ペイロードを分析し、知見を抽出・判定せよ」と指示し、事前準備で構成した必須ペイロード5項目（実態確認結果を含む）の原文を添えて渡す。

### Step 2: 情報分離（メインエージェントの責務）

verifier には、**事前準備で構成した事実ペイロードの原文**と、reflector の出力から**分離**した判定結果だけを渡す。事実を reflector の言葉で渡さない（reflector が落とした事実は verifier から見えなくなり、独立検証が同じ盲点を共有する）。

**渡す情報**:
- 事実ペイロードの**原文**（5項目。「なし」の明記を含む。要約し直さない・並べ替えない）
- **spawn 後に判明した事実**（あれば）: 原文は書き換えず、その後ろに「spawn 後に判明した事実」として追記する。対象は、reflector が返した「追加で確認した事実」と、メインが追加で確かめたこと。いずれも実行したコマンドと結果をそのまま書き、解釈は足さない
- 各知見の1行要約、カテゴリ、通過/不通過の**判定結果のみ**

**渡さない情報**（バイアス漏洩防止）:
- 不通過理由の詳細
- reflectorの推論過程
- 通過とした理由（「残す理由」「確度」）
- 反映先の候補と追記内容（案）（verifier は反映先を自分で探す。食い違いは Step 4 で扱う）

**reflector の申し送りへの対応**（verifier を呼ぶ前に済ませる）:
- **ペイロードの欠落**（必須項目が無く、「なし」の明記も無い）を指摘されたら、会話履歴から追補する。追補した事実が判定を変えうるなら、追補後のペイロードで reflector を呼び直す。変えないなら、追補を上の「spawn 後に判明した事実」に書いて進む
- **未検証の派生主張・因果**を指摘されたら、検証を実施して結果を追記する（数値の主張は反対方向の検証、因果の主張は 1 つだけを変えた再現）。実施しないなら、その主張に「未検証」と明記して渡す

### Step 3: kaizen-learning-verifier 呼び出し

**起動ゲート（縮退ケースのみ省略可）**: reflector の返却が知見0件（通過・不通過とも0）で、**かつ** ペイロードの項目 1〜3（失敗・リトライ・方針転換／ユーザーの修正指示・指摘／外部調査）がすべて「なし」の場合に限り、verifier を省略して Step 5 で「記録対象なし」と報告してよい（検証対象が論理的に存在しないため品質損失なし）。**知見0件でもペイロードに失敗等の痕跡があれば必ず起動する**（不通過にすらされなかった見落としを拾うのが verifier の役目）。

上記の省略条件に該当しない場合、Agent ツールで `kaizen-learning-verifier` を **model: sonnet** で呼び出す（`kaizen-learning-reflector` の再利用は不可。別のエージェントでなければバイアス分離が成立しない）。
プロンプトにはStep 2で分離した情報のみを渡し、独立再判定を依頼する。

### Step 4: 検証結果の統合と代替先推奨

verifierの返却結果に基づき統合する:
- **判定一致（通過）** → reflectorの提案をStep 5へ
- **判定一致（通過）だが、反映先だけが食い違う** → 下表の同名の行
- **判定一致（不通過）** → 記録不要（Step 5でその旨を提示）
- **判定不一致 / 過剰反映懸念** → メインエージェントが代替先を1案推奨し、Step 5で提示
- **未検証の主張（因果・数）** → 下の「未検証の主張への対応」

**不通過時の案内**: 横断では残さないが、プロジェクト内で再発しうる知見は、`/kaizen-update-docs` で `docs/LEARNINGS.md` への記録を推奨する旨をユーザーに案内する。

**verifier が持ち帰った新しい事実**: verifier は自分で検索・Read するので、ペイロードにも判定リストにも無い事実を根拠に、判定を返すことがある。それは検証済みの前提ではなく、新しい入力である。判定に採る前に、一次ソース（該当ファイルの該当節、コマンドの出力）で 1 回照合する。

**未検証の主張への対応**: verifier が「未検証の主張」に置いた知見は、そのままでは反映しない。

- 因果の主張: 1 つだけを変えた再現を 1 回実施する。実施しない・できないなら、原因を外し、症状と差分だけの文面に直す
- 数: 数え直す。数えられなければ、文面から数を外す
- **検証で棄却した因果の主張は、棄却の経緯ごと Step 5 で報告する**（「反証したので記録しない」だけでは、次のセッションが同じ因果をもう一度立てる）

#### 代替先推奨マトリクス（メインエージェント担当）

reflector / verifier は判定（通過/不通過）と反映先の候補を返し、振り分けの最終判断はメインが担う（両者が別々に反映先を探すので、反映先だけが食い違うことは起こりうる）。

| パターン | 推奨代替先 |
|---------|----------|
| reflector通過 / verifier過剰反映懸念 | `docs/LEARNINGS.md`（プロジェクト固有として残す） |
| reflector不通過 / verifier見落とし指摘 | `docs/LEARNINGS.md`（同プロジェクト内の再発防止） |
| reflector通過（新規扱い）/ verifier が「既存あり＝検索失敗・導線欠如」を指摘 | 知識の再記述ではなく、**タスク地点から既存記述へのクロスリンク（発見可能性）追加** |
| **失敗・非効率が起点だが該当知識は既存**（＝取り出せず／適用されず失敗。タスクが別経路で成功した場合も含む） | **「既存ゆえ記録不要」は誤り**。retrieval/発見性の是正（タスク地点からのクロスリンク・チェックリスト/トリガー追加・ナビゲーション修正） |
| 個人の好み・作業スタイル・一時的状態に該当 | auto memory |
| 一発成功した既存知識・単発判断（retrieval 失敗・導線欠如が無い場合のみ） | 記録不要 |
| **判定一致（通過）／反映先だけが食い違う**（reflector の反映先と、verifier が挙げた反映先の候補が別の節） | メインが 1 案を推奨し、Step 5 で両案を併記する。推奨の基準は「その知見が必要になる地点で読まれるか」。ファイルの行数は理由にしない |
| **要熟考** ＝ verifier が「記述の追加では止まらない」型の指摘を返した（既存の記述が、作業の地点で必ず読まれる場所に既にあったのに再発した。上の「届かなかった」行とは別で、参照を足しても止まらない）、**または**提案がスクリプトの新設・改修、手順の必須化、複数のコマンドやスキルにまたがる構造変更を含む | **即時反映しない**。`docs/NEXT_STEPS.md` への起票に回す（下の「要熟考の行き先」）。判定は、メインが提案の形と verifier の指摘から行う（reflector / verifier に分類させない） |

**auto memory推奨の判定基準**: [knowledge/meta/DOCUMENTATION_GUIDELINES.md § Auto Memory](knowledge/meta/DOCUMENTATION_GUIDELINES.md) の3基準（復元コスト・読者の存在・意思決定の根拠）の**すべてに非該当**の場合のみ。1つでも該当すればドキュメント側を選ぶ。reflectorが本来 auto memory 領域の知見を拾ったケースの救済策として位置づける。

#### 要熟考の行き先

要熟考とした提案は、その場で knowledge/ に書かない。既に記述があるのに再発した件は、記述を足しても止まらない。スクリプトや手順の必須化を含む提案は、既存の実装や過去の判断を確かめずに入れると、重複した実装や足りない修正が共有物に残る。

- **起票文を作る**（1 件につき 3 行程度）: ①何が起きたか（症状。原因は、再現で確かめたものだけ）②なぜ即時反映しないか（verifier の指摘、または提案の形）③実装の前に確かめること（同じ役割の既存のスクリプト・手順が無いか、過去に見送った判断が無いか）
- **本スキルは `docs/NEXT_STEPS.md` に書き込まない**（書くのは knowledge/ だけ）。起票文を Step 5 と Step 8 で示し、`/kaizen-update-docs` で `## Open items` に追加するよう案内する（NEXT_STEPS の書き込みは同コマンドが担う）
- 相手が配布物（kaizen-cli のコマンド・スキル・スクリプト）の不備なら、起票文に「kaizen-cli のリポジトリへ報告する」と書く（配布物はプロジェクト側から書き換えない）
- **迷ったら要熟考に倒す**。要熟考への誤判定は遅れるだけで済むが、即時反映への誤判定は、全プロジェクトが読む knowledge/ への誤記録になる

### Step 5: ユーザー確認（必須・スキップ不可）

対話形式で分析結果を提示し、ユーザーの承認を取得する。

**判定不一致または代替先推奨がある場合**: reflectorとverifierの両方の見解を明示したうえで、Step 4の代替先推奨を根拠付きで「① reflector案 / ② 代替先推奨 / ③ 記録不要 / ④ 要熟考（`docs/NEXT_STEPS.md` に起票し、前提を確かめてから実装する）」の4択で提示する。どちらか一方を暗黙に採用しないこと。

- **④ に当たる知見は、即時反映の知見と分けて提示する**（起票文を添える）
- 反映先だけが食い違う知見は、両方の反映先を併記し、推奨とその理由を添える
- 棄却した因果の主張があれば、棄却の経緯（何を固定し、何を変え、どうなったか）を報告する

**承認後の進み方**:

| 選ばれた行き先 | 続き |
|---|---|
| knowledge/ | Step 6〜9 |
| `docs/LEARNINGS.md` | `/kaizen-update-docs` を案内する（Step 6〜9 は行わない） |
| auto memory | memory ファイルを作る（Step 6 と Step 9 は不要） |
| 要熟考 | 起票文を示し、`/kaizen-update-docs` を案内する（Step 6〜9 は行わない） |
| 記録不要 | 何もしない |

### Step 6: kaizen-editing-knowledge Skill発動

承認後、ファイル編集前に以下でSkillを発動すること:
```xml
<invoke name="Skill">
<parameter name="skill">kaizen-editing-knowledge</parameter>
</invoke>
```

### Step 7: ファイル反映

適切なknowledge/ファイルに**可能な限り簡潔に**知見を反映する。反映先の選び方（`knowledge/projects/` 配下には書かない、を含む）と文面の簡潔さは `.claude/skills/kaizen-reflect-learning/CRITERIA.md § ファイル反映のルール` / `.claude/skills/kaizen-reflect-learning/CRITERIA.md § 簡潔性の原則` に従う。

- **書き込む前に、追記先の節を通読する**: 重複の確認を通っていても、新しく勧める書き方が、同じ節の別の規約と両立しないことがある。節は `bash "$KAIZEN_CLI_DIR/framework/bin/kaizen-extract-section.sh" <file> '<見出し名>'` で抽出できる。衝突するなら、衝突しない形に直してから書く
- **サイズを理由に、反映を保留しない・別テーマの節へ移さない**。追記で 800 行を超えるときも、そのまま入れて Step 8 の報告に 1 行残す（精査は `/kaizen-audit-knowledge` が担う）

### Step 7.5: 反映後整合チェック（該当行のみ必須）

Step 7 の反映内容に応じて以下を実施する。**単純追記**（行末追記・サブ注記のみで、新セクション作成・集約圧縮・受け皿新設のいずれも伴わない）の場合は全行スキップ可。

| Step 7 で行ったこと | 必須アクション |
|---|---|
| **既存セクションの集約・圧縮・別ファイルへの内容移動**（複数セクション統合、SSOT 化、大幅圧縮、行番号が大きく動く再構成を含む） | `kaizen-editing-knowledge` スキル **§ セクション集約・圧縮時の追加チェック** の grep を実行し、ヒットした参照を更新（他スキル・他 knowledge への参照陳腐化防止） |
| **knowledge/ への新セクション追加**（H3 以上、症状→対策形式の独立した項目として読める粒度） | 同ディレクトリに `INDEX.md` があれば「Find by Task / やりたいことから探す」逆引き表の最も近いカテゴリに1行追加し、`**最終更新**:` 行があれば日付・要約を更新する。未登録のまま追加すると逆引きから発見できない死蔵状態になる。対応カテゴリが無く追加先不明な場合はその旨を Step 8 で明示しユーザー判断を仰ぐ |
| **受け皿型の新セクション/新ファイル新設**（中身が薄いまま「将来の拡張枠」として作る） | 空セクションを作らない。新セクションには同セッションの知見を最低1件、実コンテンツとして入れる（受け皿だけ作ると新規作成の文脈が消えた後に空セクションが削除候補化する）。複数プロジェクトの `learnings/` を集約して受け皿を充填する横断昇格は reflect の責務外で、`/kaizen-audit-knowledge`（learning-auditor）が担当する。実コンテンツ0件で受け皿確保自体が目的なら、新設せず Step 8 でその旨を明示しユーザー判断を仰ぐ |

**チェック**: Step 8 報告の前に、各行について「実施したか / スキップ判定したか（理由）」を自問する。

### Step 8: 変更内容報告

反映した変更内容に加え、次も明示してユーザーに報告する。

- Step 7.5（反映後整合チェック）の各行の実施有無・スキップ理由
- 反映で 800 行を超えたファイル（あれば 1 行）
- 要熟考とした提案の起票文と、`/kaizen-update-docs` で `docs/NEXT_STEPS.md` に起票する案内
- 棄却した因果の主張と、その経緯

### Step 9: knowledge/ の自動コミット（git リポジトリの場合のみ）

**前提**: Step 7 および Step 7.5（該当時）の完了後に実施する。Edit と git 操作を並行実行しない（未反映状態でのコミットを防ぐため）。集約・圧縮を含む反映で Step 7.5 が必要なのに走っていない場合、本コミットは保留して Step 7.5 を完了させてから実行する。

## 昇格済み知見の誤認発覚時の修正フロー

knowledge/ へ昇格後の知見が誤りと判明した場合、以下の手順で訂正する（放置すると他プロジェクトで誤情報として参照される）。

1. **影響範囲の特定**: `bash "$KAIZEN_CLI_DIR/framework/bin/kaizen-search-knowledge.sh" <識別語>...` で、誤った記述と、それを引用した記述を列挙する（knowledge/ の実体と配布物を走査する。プロジェクトの `docs/` も見るなら `--also docs`）
   - **識別語は、装飾記号と助詞をまたがない最短の語に切る**。本文ではインラインコードや強調が語の途中に入るので、語句で探すと、誤った主張を引用した別のファイルが 0 件のまま残る（0 件になる原因の一覧: `.claude/skills/kaizen-reflect-learning/CRITERIA.md § knowledge/ の検索方法`）
   - **誤りの原因が値の出自（部分的な期間、別の条件で測った値）なら、値の語ではなく出自で洗う**: `git -C knowledge log -S "<値>" --oneline` で反映したコミットを特定し、`git -C knowledge show <commit>` で、同じ出自から入ったほかの値を列挙する
   - **数値を訂正したら、その数値が支えていた見出し・症状・対策の主張も、同じ回に見直す**（数値だけを直すと、それを根拠にした見出しが残る）
2. **訂正方針の選択**:
   - (a) **全削除**: 当該記述が完全な誤認で、保持すべき正しい知見がない場合
   - (b) **訂正して残す**: 記述の方向性は正しいが詳細が誤っている場合（誤った因果帰属を正しい因果に書き換える等）
   - (c) **反対方向の教訓に転換**: 誤認そのものから学ぶべき教訓がある場合（例: 誤ったL5 → L5訂正 + L6「自分のクエリを疑う」）
3. **プロジェクト `docs/LEARNINGS.md` の記録**: 訂正の経緯を「訂正版」として明示的に残す（単なる上書きではなく、誤認の痕跡を残して再発防止）
4. **knowledge/側の記述更新**: 同じ記述粒度で訂正。`**最終更新**:` 行があれば日付更新
5. **コミットメッセージ**: `fix(knowledge):` または `docs(knowledge): ... を訂正` と明示し、訂正であることを履歴に残す
6. **誤認の原因自体を教訓化**: reflect-learning プロセス自体の改善余地として本スキルや関連skillへの反映候補を検討（例: CRITERIA.md の「データ主張を含む知見の粒度分離」は誤認事例から追加された）

**禁止**: 誤りを静かに削除して履歴を消すこと。訂正の経緯は将来の同種ミス防止に必要。

## knowledge/ の自動コミット

knowledge/ への反映完了後、以下を実行する:

1. **今回この反映で編集・作成・削除した knowledge/ 配下のファイル**を列挙し、それだけをコミットする:
   ```bash
   bash "$KAIZEN_CLI_DIR/framework/bin/kaizen-knowledge-commit.sh" \
     -m "kaizen reflect: <知見の要約（1行、英語）>" \
     -- knowledge/<編集したファイル> knowledge/<編集したファイル>
   ```
   ファイルだけを渡す（ディレクトリは拒否される）。`git add -A` やパスを付けない `git commit` は使わない — knowledge/ は全プロジェクト・全セッションの共有物で、他セッションが編集途中のファイルまで自分のコミットに入る。
2. 出力の `[kaizen-knowledge-commit]` ブロックの `status` で分岐:

   | 終了コード | `status` | 対応 |
   |---|---|---|
   | `0` | `committed` | `message:` の件名と `committed:` のファイルが意図どおりか確認して報告 |
   | `0` | `nothing` / `skipped` | 変更なし、または git リポジトリでない。そのまま続行（警告不要） |
   | `1` | `blocked` | 今回コミットする行に壊れた参照がある（コミットはされていない）。ブロックの後ろの `MISS` 行を直し、同じコマンドを再実行する |
   | `2` | `error` | git の失敗。`git:` / `failed:` の内容を警告として表示して続行（knowledge/ の変更自体は保持されている） |
   | `3` | `error` | パス・引数の誤り。`error=` を読んで直し、再実行する |
3. `other:` の行（今回のコミットに含めなかった他の未コミット変更）があれば、**触らず**、あることをユーザーに伝える。`gate=` が `passed` 以外なら、その値を報告に含める

> 詳細: `.claude/skills/kaizen-editing-knowledge/FILE_OPERATIONS.md § knowledge/ のコミット`

# kaizen-reflect-learning 判定基準（CRITERIA）

`kaizen-learning-reflector` / `kaizen-learning-verifier` が読む判定基準の SSOT。

- **サブエージェントは本ファイルだけを読む**。反映フロー（メインエージェント専用）は同じディレクトリの `SKILL.md` にある。そこにあるのはメイン用の手順で、判定には使わない（verifier が読むと、独立した再判定にならない）
- メインエージェントも、事実ペイロードを書くとき・反映先を決めるとき・文面を書くときに本ファイルを参照する
- 本ファイルに置くのは「何を残すか・どこへ書くか・どう書くか」の基準だけで、誰がいつ何をするか（手順）は置かない

---

## 何を残すか

ここで残す記録は、次のセッションの自分や、同じ knowledge/ を読むほかのセッションが、同じ場面に立ったときのための備えである。**「これが書いてあれば、次は時間を失わない・誤らない」と見込めるものを残す**。失敗から得たものか、うまくいったことから得たものかは問わない。

- **残す価値が高いもの**: 記録が無ければ、次も試行・調査・ユーザーへの質問をやり直すことになるもの。例: 環境・ツール・サービス・データについて確かめた事実、効いた手順とそれが効く条件、ユーザーが示した期待、既存の記述の誤り・不足・届かなかった導線
- **残さないもの**: リポジトリ・コード・公式ドキュメント・その場の出力から、次回もすぐ分かること。一度きりの事情。記述が無くても確実にできること
- **失敗・リトライ・ユーザーの指摘・外部調査は強い手がかりだが、それだけでは採用の理由にしない**。「記述が無ければ、次も同じことが起きるか」で判断する。起きないと見るなら、理由を 1 行添えて不通過に置く（理由の無い不通過は、見落としと区別できない）
- **既存の記述があるのに失敗した件を、「記載済みだから不要」で終えない**。記述はあったのに届かなかった、ということである。残すのは同じ内容の再記述ではなく、届かせるための手当て（作業の地点から既存の記述への参照、チェックリストの項目、既存の記述の誤りの訂正）。その記述が、作業の地点で必ず読まれる場所（常時読み込まれる指示、呼び出したスキル・コマンドの手順）に既にあった場合は、参照を足しても止まらないので、「記述の追加では止まらない」と明記する
- **確度を書き分ける**: 確かめた事実（何で確かめたか）と推定を分ける。1 回しか見ていないことは、1 回と書く。原因の主張と数の扱いは、下の「データ主張を含む知見の粒度分離」
- **置き場は、横断かプロジェクト固有かで分ける**: ほかのプロジェクトでも同じ場面が起きるなら knowledge/（下の「ファイル反映のルール」）。このプロジェクトでしか起きないなら不通過とし、その旨を理由に書く（プロジェクトの `docs/LEARNINGS.md` に残すかは、メインエージェントが案内する）

判定は「通過（残す）」「不通過（残さない）」の 2 値で返す。

この節は以前「一般化テスト」（条件 1〜3。失敗・リトライが起きた情報は無条件で採用する）だった。型で採否を決める規則は、既に書いてあるのに守れなかった件まで通過させ、記述を増やすだけになる。型の指定をやめ、目的の記述に置き換えた。

## 抽出カテゴリ（9カテゴリ）

何を残すかは、上の「何を残すか」で決める。本節は、素材がセッションのどこに出やすいかと、知見の型を引くための表である。**全カテゴリを埋めるチェックリストではない**（該当の無いカテゴリは報告しなくてよい）。

### 1. 失敗パターンと成功アプローチの対比

- 試行錯誤が発生した箇所を特定（例: ツール仕様の勘違い、API/CLIの誤用）
- 失敗したアプローチと最終的に成功したアプローチを明確に対比
- 「次回は一度目から成功する」ためのガイドラインとして記録

### 2. 暗黙のルールの明文化

- ユーザーが修正指示を出した箇所を特定
- 修正指示の背景にある「期待される動作」「暗黙のルール」を抽出
- 明文化されていなかったルールをknowledge/に追加し、次回から自動的に従えるようにする

### 3. 技術的な誤解・勘違い

- ツールやサービスの仕様誤解、パラメータの誤用
- コマンド実行の失敗とその原因
- 正しい理解・正しい使い方を記録

### 4. 情報探索の非効率の検出

- 検索を複数回やり直した、間違った候補を提示した、ユーザーに正解を教えてもらった箇所を特定
- 「探すのに苦労した」= knowledge/の該当領域に情報が不足しているシグナル
- 不足していた情報を適切なknowledge/ファイルに追加

### 5. 新規ドメイン知識

- 新しく扱った技術・ツール・サービスの概要
- 公式ドキュメント・リファレンスの参照先
- 適切なknowledge/ファイルへの追加を検討

### 6. 業務・プロジェクト横断パターン

- 複数プロジェクトに共通するパターンや手法
- 再利用可能なアプローチや設計判断
- 汎用化してknowledge/に追加

### 7. 判断の失敗

- 論理的には正しいが、考慮不足で現実的に間違った結論・設計判断を出した箇所を特定
- 見落とした観点（前提条件の未確認、エッジケース、実運用パターン等）と、正しい判断に至るために必要だったチェックを記録
- カテゴリ3との違い: カテゴリ3は「技術的に間違い」（API仕様の勘違い等）。本カテゴリは「技術的には動くが、判断・解釈が間違い」

### 8. 既存知見の精度改善

- **トリガー**: knowledge/やSkillの既存セクションを参照して作業したが、説明が不足していた・不正確だった・手順に追加ステップが必要だった
- **抽出内容**: 既存セクションの具体的な改善点（何が不足/不正確で、どう修正すべきか）
- **反映先**: 該当するknowledge/ファイルの既存セクションを更新（skills/は静的のため対象外）
- **他カテゴリとの違い**: カテゴリ1-7は新規知見の追加。本カテゴリは既存知見の品質向上（書き直し・補足・修正）

### 9. 外部調査で得た知識の還元（Query Filing Back）

- **トリガー**: セッション中に WebFetch / WebSearch / MCP（context7、AWS Documentation 等）/ その他の外部ソースを参照して情報を得た（失敗の有無を問わない）
- **抽出内容**: 外部調査で得られた知識のうち、knowledge/に記載があれば次回以降の外部調査が不要になるもの
- **反映先**: 該当するknowledge/ファイル
- **カテゴリ4との違い**: カテゴリ4は「探索の失敗・非効率」がシグナル。本カテゴリは「外部調査の実施」自体がシグナル。一発で見つかった場合も対象
- **「何を残すか」との関係**: 失敗の有無は問わない。次回の外部調査を省けると見込めるものを残す（調べ直せばすぐ分かることは残さない）

## 手順から外れた箇所の読み方

ペイロードには、呼び出したスキル・コマンドの手順から外れた箇所が、4 つの型で列挙される。外れたこと自体は失敗ではない。**手順と実際の作業が食い違ったという事実が、どちらかに直すところがあることを示す**。

| 型 | 手順の側に問題があるなら |
|---|---|
| 従わなかった項目 | その項目の条件が広すぎる（当てはまらない場合まで指示している） |
| 自主的に足した確認 | 手順に穴がある（必要な確認が書かれていない） |
| 書き換えた箇所 | 手順が実態と合っていない |
| 回避した箇所 | 手順の求める値・確認が、その場面では満たせない |

- **1 件ずつ、どちらの側の問題かを読む**: 「手順の不備」（上の表が当たる）か、「外れた側の誤り」（手順は妥当で、従うべきだった）か。手順の該当箇所を実際に開いて確かめる（ペイロードの要約だけで決めない）
- **「手順の不備」は、knowledge/ に書いても直らない**。スキル・コマンドは静的で、反映の対象ではない（下の「ファイル反映のルール」）。通過・不通過の一覧には置かず、読みとして返す: どのファイルのどの記述を、どう直せばよいか。配布物（`kaizen-` で始まるもの）か、プロジェクト独自のものか
- **「外れた側の誤り」は、書いてあるのに従わなかった件である**。その手順は呼び出した時点で読まれているので、「何を残すか」の「記述の追加では止まらない」に当たる
- 外れた理由の中に、手順とは別に横断で使える事実（ツールの仕様、環境の制約）があれば、それは通常の知見として「何を残すか」で判定する

## 昇格候補の扱い

ペイロードには、プロジェクトの `docs/LEARNINGS.md` に書かれた昇格候補（`candidate:` の行）が含まれることがある。プロジェクト側の棚卸しが、横断で残すべきだと一度判定したものである。

- **判定を引き継がない**。「何を残すか」で改めて判定する。見るのは、ほかのプロジェクトでも同じ場面が起きるか、プロジェクト固有の事情（名前・構成・業務）を除いても教訓が残るか
- **`[open]` の候補は、1 件ずつ、通過か不通過のどちらかに必ず置く**（置かれなかった候補は、次の回も同じ行のまま残る）。`[deferred]` の候補は、再検出条件が成立したと書かれているものだけを判定する
- **既に knowledge/ に入っていないかを、検索して確かめる**（下の「knowledge/ の検索方法」）。入っていれば不通過とし、理由に所在（ファイルと節）を書く — プロジェクト側は、それを見てマーカーを書き換える
- 候補の行だけで本文が添えられていない場合は、推測で補わず、ペイロードの欠落として返す

## データ主張を含む知見の粒度分離

数値比較・クエリ結果差異・集計値の不一致を根拠とする知見は、根拠を以下の 2 つに分けて扱う。

- **Raw measurements（生観測）**: 「クエリAは504を返した」「CSVには9,576が記載」等、単独で観測された事実
- **Derived claims（派生主張）**: 「真値は◯◯」「片側が過小/過大」「倍率がNXに達する」等、比較・推論を経た結論

派生主張は、**反対方向の検証を1つ以上**通したものだけを事実として扱う。例: 「A側が過小」仮説なら「B側が過大ではないか」の確認として JOIN 重複要因の切り分け等を行う。

検証結果（実行したコマンドとその出力）が添えられていない派生主張は、**未検証**として扱う。未検証の派生主張を事実として前提に置くと、それを受け取った側は同じ前提の上で判定するため、独立検証が成立しない。

### 因果の主張にも同じ分離が要る

「X を変えたら直った」と書いた時点で、原因の帰属という派生主張が入る。トラブルシュートでは複数の変更を同時に入れて成功に至るのが普通で、どの変更が効いたかは、成功したという事実からは分からない。

- **Raw**: 「コマンド A は 0 件を返した」「その後コマンド B は 3 件を返した」＋ **A と B の差分すべて**（何を変えたかの全列挙）
- **Derived**: 「原因は、差分のうちの 1 つだった」

差分が 2 つ以上あるなら、**1 つだけを変えた再現を 1 回**通したものだけを、原因として扱う。通していなければ、症状と差分（Raw）だけを書き、原因は書かない。knowledge/ の既存の記述と食い違う一般則を立てるときは、この再現を必ず通す（既存の記述の方が正しい可能性を、先に潰す）。

汎用例: ログの検索が 0 件だったので、検索語の引用符と時間の範囲を同時に直したら 3 件返った。「引用符が原因」と書く前に、範囲を固定して引用符だけを元に戻すと、やはり 3 件返った。原因は範囲だけで、引用符についての既存の記述は正しかった。

### 回数・時間・件数は数え直す

「4 回ほど」「数十秒」「十数回」のような数は、記憶で書かない。数え直すか、数えていなければ「未計数」と書く。概数のまま渡すと、受け取った側はそれを観測として扱う。

## ファイル反映のルール

**反映先はknowledge/のみ**: skills/は静的ファイルであり、reflect-learningの対象外。

1. **既存ファイルへの追記を優先**: 該当する領域のknowledge/ファイルに追記
2. **新規ファイル作成は最後の手段**: 既存ファイルで対応できない領域の知見であることが明確な場合のみ
3. **プロジェクト固有情報は追加しない**: knowledge/はプロジェクト横断。プロジェクト固有の教訓は `/kaizen-update-docs` で `docs/LEARNINGS.md` に記載
4. **`knowledge/projects/` 配下には書かない**: `projects/details/` は PROJECT_SUMMARY の、`projects/learnings/` は LEARNINGS のコピーで、`/kaizen-update-docs` が同期するレジストリの派生物である（手で書いた内容は次の同期で上書きされる）。検索でここにヒットしても反映先の候補にせず、`knowledge/` 直下の各カテゴリディレクトリか `knowledge/meta/` から探す
5. **追記先の節の、既存の規約と衝突しないか確かめる**: 重複の確認（同じ知見が既にあるか）とは別の問いで、**新しく勧める書き方・手順が、同じ節の別の規約と両立するか**を見る。「X と書け」という追記は、同じ節の「X は削除される」という規約と正面から衝突しうる。追記位置の前後数行では足りないので、追記先の節を通読する。衝突するなら、衝突しない形に直してから反映する
6. **サイズを反映先の決定理由にしない**: 反映先は「その知見が必要になる地点で読まれるか」で決める。行数が多いことを理由に、別のファイルへ移す・反映を保留する、という提案をしない（下の「簡潔性の原則」）

## knowledge/ の検索方法

「この知見は既に書かれているか」は、次の 1 コマンドで調べる（プロジェクトルートで実行する）:

```bash
bash "$KAIZEN_CLI_DIR/framework/bin/kaizen-search-knowledge.sh" <識別語> [<識別語>...]
```

- 走査するのは、`knowledge/` の実体（`projects/` を除く）と、配布物の skills / commands / agents。照合は固定文字列で行う（正規表現ではない）
- 識別語は、コマンド名・API 名・エラー文言・概念名から 2〜3 個選ぶ。**装飾記号や助詞をまたがない最短の語**にする
- `-` で始まる語（`--commit`、`-exec` など）は、`--` の後ろに置く: `… kaizen-search-knowledge.sh -- "--commit" "gh run"`。`--` が無いとオプションとして読まれ、`status=error`（終了コード 3）で検索されない
- ヒットしたファイルは Read ツールで読む（knowledge/ はシンボリックリンクであり、Glob ツールはシンボリンク先を辿れない）

出力の読み方:

| 行 | 意味 |
|---|---|
| `area:` / `not-scanned:` | 走査した場所と、走査できなかった場所 |
| `[K]` | 識別語ごとのヒットファイル。`knowledge/...` はそのまま Read できる。`framework/...` は `area:` 行に出ているパスからの相対 |
| `[H]` | ヒット行と、その行を含む節の見出し（`§`）。**その節を読んでから判定する**（ヒット行の 1 行だけで「記載済み」と決めない） |
| `[S]` | knowledge リポジトリの未コミット変更。反映先の候補がここに出ていれば、別のセッションが同じ知見を書いている途中かもしれない。重ねて書き足さず、その追記への統合として提案する |
| `status=partial`（終了コード 1） | 走査できなかった場所がある。`not-scanned:` / `warning:` に出た対象については、0 件を根拠にしない |
| `status=error`（終了コード 2・3） | 検索は実行されていない。結果が無いことを 0 件と読まない |

### 0 件は「記述が無い」ことを意味しない

検索が 0 件を返す原因は、記述の不在のほかに 8 つある。「既存記述なし」と結論する前に、どれにも当たらないことを確かめる。

| # | 0 件になる原因 | 対処 |
|---|---|---|
| 1 | **symlink の取りこぼし**: `grep -r ... knowledge/` は、symlink の先を辿らずに 0 件を返すことがある | 上のスクリプトを使う（実体パスを走査する）。自分で `grep -r` を組まない |
| 2 | **走査範囲の不足**: `knowledge/` だけを見て、skills / commands / agents に書かれた規約を見ない | 同上（3 つとも走査する）。プロジェクトの `docs/` も見るなら `--also docs` を足す |
| 3 | **表記揺れ**: スペースの有無、全角と半角、英語と日本語のどちらで書くか | 表記を変えた語を並べて渡す（`"S3 コネクタ" "S3コネクタ" "S3 connector"`）。大文字と小文字の違いは `-i` |
| 4 | **実装形式を仮定した検索語**: `register()` で探すと、`case` 分岐の `register)` や別名の定義に当たらない | 識別子だけ（`register`）で探す。絞り込みは結果を見てから行う |
| 5 | **探索ファイルの絞りすぎ**: 当たりを付けたファイルだけを検索する | 先に全体を検索する。ファイル名の当たりは、結果を絞るときに使う |
| 6 | **Markdown の装飾が語の途中に入る**: 本文は `` `git diff` を読む `` や `**X** を確認` のように書かれ、装飾をまたぐ語句は一致しない | 装飾が入らない最短の識別語に切る（`git diff を読` ではなく `git diff`）。書き方の揺れではないので、表記を増やしても当たらない |
| 7 | **`head -N` による打ち切り**: 検索の出力を `head` に通すと、一致はしているのに、先頭の N 行が無関係なヒットで埋まる | 不在を結論づける検索に `head` を付けない。`[K]` は全件が出る。`[H]` が打ち切られたら（`the first N of M files`）、語を絞って再実行する |
| 8 | **検索コマンド自体の失敗**: 失敗した検索は何も出力せず、0 件と同じに見える | 終了コードと `status=` を見る。`[K] "...": 0 file(s)` の行が出ていない 0 件は、検索結果ではない |

## 簡潔性の原則

- 箇条書き優先、長文説明は避ける
- 例示は最小限（1例のみ）
- コード例は25行以内
- 重複排除、既存内容と統合
- **既存の節への追記を、節の新設より優先する**: 同じ症状・同じ対象の節があれば、そこへ足す。新設するのは、その知見を探すときの語（症状・エラー文言・対象名）が既存のどの節にも無い場合だけ
- **サイズを理由に、内容を削らない・反映を保留しない・別テーマの節へ同居させない**: 圧縮してよいのは表現までで、線引きは下の表。別テーマの節へ同居させると、探す語で見つからなくなり、再発防止という記録の目的に反する
- **追記で反映先が 800 行を超えるとき**: 記録はそのまま入れ、超えたことを反映の報告に 1 行残す。その場で内容を削らない。精査と分割は `/kaizen-audit-knowledge` が担う（600 行超・800 行超を警告する）

| 圧縮してよい（表現） | 削ってはいけない（内容） |
|---|---|
| 冗長な言い回し・同義の反復 | 実例の 1 例目（再現条件・実測値・日付を担う） |
| 既出の内容の再説明（既存の節への参照に置き換える） | 検証状況の但し書き（1 回だけの観測・未検証の因果・外挿の注記） |
| 散文の列挙（表・箇条書きにする） | 断定を弱める条件、症状から探すための語 |
| 2 例目以降の実例（1 例目と同じ仕組みなら） | 対策の各手順（手順の数を減らして短くしない） |

# kaizen-learning-auditor

`knowledge/projects/learnings/` 配下の教訓ファイルを横断的にスキャンし、`knowledge/` への昇格候補を検出・提案するサブエージェント。
**ファイル編集は行わない**（分析と提案のみ）。

knowledge/ はシンボリックリンクのため、ファイルアクセスには Read ツールで直接パスを指定すること。実体パスは `readlink -f knowledge` で取得できる。

---

## 昇格の原則

### 昇格判定基準

以下のいずれかを満たす教訓は `knowledge/` への昇格候補:

- **複数プロジェクトで再発**: 2 つ以上のプロジェクトで同種の失敗・教訓が記録されている
- **プロジェクト非依存の仕様起因**: AWS / 外部サービス / 標準ライブラリ等の仕様に起因し、どのプロジェクトでも再発しうる
- **失敗・リトライに基づく知見**: セッション中に失敗が発生した情報は再発防止のために記録価値が高い

### 昇格しない教訓

- プロジェクト固有のテーブル名・ARN・ビジネスロジックに依存する教訓
- 単発の例外や一度きりの判断
- `→ knowledge/` マーカー済みのエントリ（昇格済み）

---

## 手順

### Step 1: learnings/ ファイルの収集

1. `$(readlink -f knowledge/projects/learnings)` 配下の `.md` ファイルを一覧取得
   ```bash
   find "$(readlink -f knowledge/projects/learnings)" -name "*.md" -type f | sort
   ```
2. 各ファイルを読み込み、`### ` 見出しで区切られた個別エントリを抽出
3. 各エントリから以下を抽出:
   - プロジェクト ID（ファイル名から `{id}.md` → `{id}`）
   - タイトル（`### ` 見出し）
   - 日付（見出し内の括弧 or `**Date**:` / `**記録日**:`）
   - キーワード（サービス名、エラー名、技術用語）
4. 5 行未満のファイル（テンプレートのみ）はスキップ
5. `INDEX.md` があれば対象外（ナビゲーション用）

### Step 1.5: 昇格マーカー検出

各エントリ内に以下のいずれかを含む行があるか確認する:

- `→ knowledge/<path>.md § <section>` を含む `- **Promoted**:` / `- **昇格先**:` bullet

正規表現: `→\s+knowledge/[^\s§]+(\.md)?\s+§\s+.+`

マッチしたエントリは「カバー済み」扱いで昇格候補から除外する。ただし Step 3 のクロスプロジェクトキーワードグルーピングには引き続き参加させる（再発パターンの可視化には必要）。

1 エントリに複数の `→ knowledge/` 行がある場合、すべてをカバー先として扱う。

### Step 2: knowledge/ との重複チェック

カバー済みでない各エントリについて:

1. エントリから特徴的なキーワードを 2-3 個抽出
2. `grep -rn "<キーワード>" "$(readlink -f knowledge)" --exclude-dir=projects` で検索（`projects/` 配下は自己参照になるため除外）
3. ヒットした場合、該当セクションを読んで内容がカバーされているか判定
4. 分類:
   - **カバー済み**: knowledge/ に同等の知見が存在
   - **部分カバー**: 関連セクションはあるがこの具体例は未記載
   - **未カバー**: 関連する knowledge/ 記述なし

### Step 3: クロスプロジェクトパターン検出

1. Step 1 で抽出したキーワード・テーマでエントリをグルーピング
2. 2 つ以上のプロジェクトに類似テーマのエントリがある場合、クロスプロジェクトパターンとして記録
3. 各パターンについて共通テーマを要約

カバー済みエントリも参加させる（複数プロジェクトでの再発を可視化するため）。

### Step 4: 昇格候補の選定

以下の優先順で候補を選定:

1. **優先度 1**: クロスプロジェクトパターン（Step 3）かつ未カバー / 部分カバー（Step 2）
2. **優先度 2**: 単一プロジェクトだがプロジェクト非依存の仕様起因かつ未カバー

各候補について以下を特定:

- 反映先の `knowledge/<topic>/<file>.md § <section>`（grep 結果から推定）
- 反映方法: 新規セクション追加 / 既存セクションに追記
- 提案内容: 1-3 行の簡潔な記述案（簡潔性の原則を遵守）
- 確信度: 高 / 中

### Step 5: 保護判定

各候補について以下をチェックし、該当すれば候補から除外:

- プロジェクト固有のテーブル名・ARN・ビジネスロジックを含むか
- 一般化すると適用条件が落ち、不適切な場面で誤適用されるリスクがあるか
- 単発の例外か（条件 1: パターンが単発でない）

### Step 6: 結果を返却フォーマットで出力

## 返却フォーマット

各セクションは候補がゼロ件の場合「候補なし」と**必ず明記する**（見出しごと省略しない）。サマリーの数値は X=0 / N=0 等で必ず表示する。`kaizen-knowledge-auditor` の「統合候補なしと明記する」パターン（同 § 2.6 末尾）と一貫させ、メインエージェントが結果の取りこぼしか auditor が走ったが空かを区別できるようにする。

```markdown
## 教訓横断レビュー

### サマリー

- 対象ファイル数: X（Y ファイルスキップ: 5 行未満）
- 教訓エントリ総数: Z
- クロスプロジェクトパターン: N 件
- 昇格候補: M 件（高確信 X, 中確信 Y）
- カバー済み: K 件

### クロスプロジェクトパターン

#### パターン 1: [パターン名]

- **検出プロジェクト**: project-a (§ セクション名), project-b (§ セクション名)
- **共通テーマ**: [共通する教訓の要約]
- **昇格判定**: 候補 / カバー済み / プロジェクト固有

候補がない場合は「クロスプロジェクトパターンなし」と明記する。

### 昇格候補

#### 候補 1: [教訓の要約]

- **出典**: [project-id] § [セクション名]（[日付]）
- **昇格理由**: 複数プロジェクト再発 / プロジェクト非依存の仕様起因
- **反映先**: knowledge/[path].md § [セクション名]
- **反映方法**: 新規セクション追加 / 既存セクションに追記
- **提案内容**: [1-3 行の簡潔な記述案]
- **確信度**: 高 / 中

候補がない場合は「昇格候補なし」と明記する。

### カバー済み教訓（参考）

- [project-id] § [教訓名] → knowledge/[path].md § [セクション名] でカバー済み

マーカー付きエントリがない場合は「カバー済み教訓なし」と明記する。

## ログ用サマリー（AUDIT_HISTORY.md 追記用）

メインエージェントがこのブロックを `knowledge/meta/AUDIT_HISTORY.md` にそのまま追記する。
以下のフォーマットに値を埋めて**必ず出力すること**（省略不可）。

### YYYY-MM-DD — projects/learnings/

- **対象**: X ファイル / Y エントリ
- **クロスプロジェクトパターン**: N 件
- **昇格候補**: M 件（高確信 X, 中確信 Y）
- **カバー済み**: K 件（`→ knowledge/` マーカー付き）
- **特記**: [繰り返しパターンがあれば「繰り返し: XXX（前回: YYYY-MM-DD）」、なければ省略]

注: エントリは `### YYYY-MM-DD` の見出しレベル（`## ログ` のサブセクション）。

## メインエージェントへの申し送り

1. 上記候補をユーザーに提示し、承認を得ること
2. 承認された候補について `kaizen-editing-knowledge` Skill を発動してから編集
3. 「ログ用サマリー」ブロックを `knowledge/meta/AUDIT_HISTORY.md` の末尾（`**Last updated**:` / `**最終更新**:` 行の直前）に追記し、日付を更新
4. 個別候補の採用/却下が確定したら、追記したエントリに `- **実施結果**: ...` 行を追加。各候補は以下のタグで分類する: `[採用/Adopted]` / `[保護/Protected]` / `[補完/Supplemented]` / `[スコープ外/Out-of-scope]` / `[過剰/Overreach]`

**元プロジェクトの `docs/LEARNINGS.md` への手動マーキングは不要**。次回 `/kaizen-update-docs` 実行時に `learnings/{id}.md` へ再 sync されるため、ユーザーが元の `docs/LEARNINGS.md` に `- **Promoted**: → knowledge/...` 行を追加すれば、その後の audit で auditor が自動的にカバー済みとして検出する。
```

---

## 制約

- **ファイル編集は行わない**: 分析と提案のみが責務。Edit / Write ツールは使用不可
- **確信度「中」の候補**: 理由を詳しく記述し、判断をユーザーに委ねる
- **5 行未満のファイル**: テンプレートのみのためスキップ
- **昇格済みエントリ**: `→ knowledge/` マーカー付きは候補から除外（Step 3 のグルーピングには参加）
- **`knowledge/projects/` の grep 除外**: Step 2 で `--exclude-dir=projects` を付け、自己参照（learnings/ 同士のヒット）を防ぐ

# kaizen-knowledge-auditor

knowledge/ファイルを定期的にスキャンし、削減可能な情報を検出・提案するサブエージェント。
ファイル間のSSOT違反（内容重複）も検出する。
**ファイル編集は行わない**（分析と提案のみ）。

---

## 精査の原則

### 運用可能性基準

「知っていること」と「確実に運用できること」は異なる。削減対象は**知っていてかつ確実に運用できる**情報のみ。

- 知っているが運用で間違えやすい情報 → 保持
- 知っていて確実に正しく運用できる情報 → 削減候補

### 失敗事例の保護

実際の失敗・事故に基づく情報は、内容が自明に見えても削減対象外。失敗から学んだ運用知見は再発防止のために不可欠であり、一般知識とは区別する。

## 手順

### 1. DOCUMENTATION_GUIDELINES.md を読む

精査の観点（6項目）を把握する。

```
knowledge/meta/DOCUMENTATION_GUIDELINES.md
```

knowledge/ はシンボリックリンクのため、ファイルアクセスには Read ツールで直接パスを指定すること。
symlink先の解決が必要な場合は `readlink -f knowledge` で実体パスを確認する。

### 2. 対象ファイルの収集

knowledge/ 配下の `.md` ファイルを一覧取得する。

```bash
find "$(readlink -f knowledge)" -name "*.md" -type f | sort
```

- **ディレクトリ指定あり**: 指定ディレクトリに絞る（例: `meta/`）
- **指定なし**: knowledge/ 全体を対象
- **除外**: 100行未満のファイルは精査対象外（コスト対効果が低い）
- **除外**: INDEX.md ファイルはナビゲーション用のため対象外

#### 鮮度の算出

各ファイル末尾の `**Last updated**:` または `**最終更新**:` から現在日付までの経過日数を算出し、鮮度を分類する。

| 経過日数 | 鮮度 | 精査への影響 |
|---------|------|------------|
| 90日以内 | ✅ | 通常精査 |
| 90日超 | ⚠️ | 精査優先度を上げる。Step 3で陳腐化チェックを追加実施 |
| 180日超 | 🔴 | 上記に加え、セクション単位での利用実態確認を実施 |

**注意**: 鮮度が低い＝削減ではない。命名規則・用語等の安定した知識は長期間未更新でも有効。鮮度は精査の優先順位付けと、陳腐化リスクの重点確認に使う。

### 2.5. ファイル間重複スキャン

対象ファイルを読んだ後、ファイルをまたいで内容が重複していないかをチェックする。

**チェック観点**:

1. **セクション見出しの重複**: 複数ファイルに同名・類似名のセクション（`##` / `###`）がないか確認。同名セクションがあれば内容を比較し、重複の有無を判定
2. **固有名詞の重複**: 同じパス・名前・用語等が複数ファイルに記載されていないか確認。「発見の起点として名前だけ言及」と「詳細な説明」は区別する（前者は重複ではない）

**検出時の出力**: 重複ペアごとに以下を報告

- 重複しているファイル名とセクション名
- 重複の種類（見出し重複 / 固有名詞重複）
- どちらをSSOT（正）とすべきかの提案と理由

**返却**: 監査レポートの「SSOT違反候補」セクションにまとめる。

### 3. 各ファイルのスキャン

ファイルごとに以下の観点で削減候補を抽出する。

**精査の観点6項目**（DOCUMENTATION_GUIDELINES.md準拠）:

1. 重複の削除
2. 冗長な出力例の削減
3. 長いスクリプト例の簡潔化（25行超）
4. セクションの統合
5. 情報の階層化
6. AIモデルにとって自明な内容の削減

#### 陳腐化チェック（鮮度⚠️以上のファイルに追加実施）

通常の6項目に加え、以下を確認する:

- 外部サービスの仕様変更・API廃止が反映されていない記述はないか
- ツールのアップデートで変わった挙動・パラメータはないか

#### 参照可能性チェック（鮮度⚠️以上のファイルに追加実施）

各セクション（`##` / `###`）が以下のいずれかから参照されているか確認する:

- INDEX.md の「Find by Task」テーブル
- スキルファイル（`.claude/skills/` 配下）
- 各プロジェクトの CLAUDE.md

**参照なしのセクションが見つかった場合**:
- 有用な情報だが導線がない → INDEX.md への導線追加を提案
- 不要になった情報 → 削減候補として報告

鮮度と組み合わせて判断する: 鮮度🔴で参照なし＝不要の可能性が高い。鮮度⚠️で参照なし＝導線不足の可能性が高い。

**項目6のサブ基準**（特に注意深く判定）:

- (a) 一般的なプログラミングパターン（dict.get、try/except基本形等）
- (b) 標準的なツールのベストプラクティス（CLIの基本使用法等）
- (c) フレームワーク/ツールの基本的な使い方（基本コマンド等）
- (d) 一般的なメリット・デメリット説明

### 4. 保護判定

各候補について以下をチェックし、**1つでも該当すれば候補から除外**する:

- ドメイン固有のコンテキスト（用語、パス、チーム固有パターン）を含むか？
- 事故事例・失敗パターンに基づく記述か？
- 「なぜこうすべきか」の運用判断を助ける文脈があるか？（単なるHowではなくWhyが含まれるか）
- 省略すると誤った運用をするリスクがあるか？
- コード例が教訓・事例の証拠として密結合しているか？（参照リンク化すると文脈が切れる場合は保護）
- 意図的な設計基準として配置されているか？（AIが生成可能でも「プロジェクトの基準明示」として価値がある場合は保護）
- 発見の起点となる情報か？（パス名・用語等、「存在を知ること自体が価値」の情報は保護）

### 4.5. 結論の自己検証

削減候補が少ない・ゼロの場合でも、以下を自問してから結果を出力する:

- **観点の偏り**: 6項目の精査観点のうち、十分にチェックできていないものはないか？
- **保護判定の過剰適用**: 安易に「保護」と判断していないか？固有情報でも冗長な記述は削減可能
- **ファイルサイズの見落とし**: 600行超のファイルに対して「問題なし」としていないか？

新たな候補が見つかった場合、Step 3の候補リストに追加する。

### 5. 結果を返却フォーマットで出力

## 返却フォーマット

以下の形式で結果を出力すること。

```markdown
## 監査レポート

### サマリー

- 対象ファイル数: X
- 候補検出数: Y
- 推定削減行数: Z
- knowledge/総行数: N（前回比較用）

### 鮮度テーブル

| ファイル | 行数 | 最終更新 | 経過日数 | 鮮度 |
|---------|------|---------|---------|------|
| GETTING_STARTED.md | 200 | 2026-03-15 | 24日 | ✅ |

### 削減候補

#### [ファイル名] (現在XX行)

- **候補1**: [セクション名 / 行範囲]
  - 該当観点: [精査の観点の番号]
  - 現在の内容（要約）: [何が書かれているか]
  - 削減方法: 全削除 / 要約に置換 / 参照リンクに置換
  - 推定削減行数: X行
  - 確信度: 高 / 中
  - 理由: [なぜ削減可能と判断したか]

### SSOT違反候補（ファイル間重複）

- **重複1**: [ファイルA § セクション] ↔ [ファイルB § セクション]
  - 種類: 見出し重複 / 固有名詞重複
  - SSOT提案: [どちらに寄せるか] — 理由: [なぜそちらが正か]

### 保護対象（参考）

- **[ファイル名] § [セクション]**: 一見自明だが [理由] のため保護

## メインエージェントへの申し送り

1. 上記候補をユーザーに提示し、承認を得ること
2. 承認された候補について kaizen-editing-knowledge Skill を発動してから編集
3. 編集後 knowledge/ を自動コミット
```

---

## 制約

- **ファイル編集は行わない**: 分析と提案のみが責務。Edit/Write ツールは使用不可
- **確信度「中」の候補**: 理由を詳しく記述し、判断をユーザーに委ねる
- **小ファイルスキップ**: 100行未満のファイルは精査対象外

# Reflect cross-project learnings

現在のClaude Codeコンテキスト（今日のいままでの作業履歴）から得られた知見を分析し、
プロジェクト横断のknowledge/ファイルに**簡潔に**反映する。

**言語**: ユーザーの言語に合わせて応答すること

**サブエージェント委譲**: 調査フェーズを `kaizen-learning-reflector` に、独立検証を `kaizen-learning-verifier` に委譲する。情報分離（reflectorの推論過程をverifierに渡さない）はメインエージェントの責務。

**実行フロー**:

### 事前準備（Step 1 の前に必ず実施）

以下の2点を先に行い、結果を Step 1 の reflector spawn プロンプトに含める。reflector spawn と並行させないこと（情報の取りこぼしを防ぐため）。

1. **外部情報取得ツールの列挙**: セッション中に使用した外部情報取得ツール（WebFetch、WebSearch、`mcp__context7__*`、`mcp__aws-documentation-mcp-server__*` 等）を洗い出す。カテゴリ9（外部調査知識の還元）の検出漏れ防止のため、長いセッションでは特に明示的に列挙する。
2. **事実主張の実態確認**: セッション中に「ファイル / symlink / 環境変数 / 設定が◯◯の状態である」という事実主張があった場合、推測のまま渡さず `ls -la` / `readlink -f` / `printenv` 等で現物確認してから reflector に渡す。他端末ブランチのマージレビュー時にも同じ実態確認を行うこと（追加された path/symlink/環境依存記述が自端末で成立するか確認）。

### Step 1: kaizen-learning-reflector 呼び出し

Agent ツールで `kaizen-learning-reflector` を呼び出し、分析結果を取得する。
プロンプトには「セッション中の作業履歴を分析し、知見を抽出・判定せよ」と指示し、事前準備で得た外部ツール使用履歴・実態確認結果を添えて渡す。

### Step 2: 情報分離（メインエージェントの責務）

reflectorの出力から以下を**分離**してStep 3でverifierに渡す:

**渡す情報**:
- 「事実情報」セクション（作業概要、失敗箇所、ユーザー指摘、探索経緯）
- 各知見の1行要約、カテゴリ、通過/不通過の**判定結果のみ**

**渡さない情報**（バイアス漏洩防止）:
- 不通過理由の詳細
- reflectorの推論過程
- 通過条件の判定根拠

### Step 3: kaizen-learning-verifier 呼び出し

Agent ツールで `kaizen-learning-verifier` を **model: sonnet** で呼び出す。
プロンプトにはStep 2で分離した情報のみを渡し、独立再判定を依頼する。

### Step 4: 検証結果の統合

verifierの返却結果に基づき統合する:
- **判定一致** → そのまま採用（reflectorの提案をStep 5へ）
- **判定不一致** → 両方の見解をStep 5でユーザーに提示し、最終判断はユーザーに委ねる
- **過剰反映の懸念** → 懸念点を含めてStep 5で提示する

### Step 5: ユーザー確認（必須・スキップ不可）

対話形式で分析結果を提示し、ユーザーの承認を取得する。
判定不一致がある場合、reflectorとverifierの両方の見解を明示し、ユーザーに最終判断を求める。

### Step 6: kaizen-editing-knowledge Skill発動

承認後、ファイル編集前に以下でSkillを発動すること:
```xml
<invoke name="Skill">
<parameter name="skill">kaizen-editing-knowledge</parameter>
</invoke>
```

### Step 7: ファイル反映

適切なknowledge/ファイルに**可能な限り簡潔に**知見を反映する。

### Step 8: 変更内容報告

反映した変更内容をユーザーに報告する。

### Step 9: knowledge/ の自動コミット（git リポジトリの場合のみ）

下記「knowledge/ の自動コミット」セクションに従う。

## 一般化テスト（基準定義）

エージェントが参照するSSOT。抽出した知見が以下の条件を満たすか判定する。

- **条件1**: パターンが単発の例外や一度きりの判断ではない
- **条件2**: 一般化によってタスク遂行の効率が明確に向上し、かつ既存仕様を毀損しない
- **条件3（無条件採用）**: セッション中に失敗・リトライが発生した情報は無条件で採用
  - ✅ 無条件採用: エラー発生→修正して再実行した情報（「知っているはず」でも実際に失敗した = 記録が必要）
  - ✅ 追加する: 公式ドキュメント等で調査が必要だった情報（基本仕様であっても）
  - ❌ 追加しない: Claudeの既存知識で即座に回答でき、**かつセッション中に失敗していない**情報
- **条件3(補足)**: 条件3で通過した知見が既にknowledge/の別ファイルに記載済みの場合、「記載済みだから不要」と判断してはならない。「記載済みなのに失敗した＝ドキュメントの配置・粒度が不十分」と判断し、より発見しやすい場所への追加や既存記載の改善を提案すること
- **除外条件の例外（カテゴリ9）**: 外部ソース（WebFetch、MCP、context7等）を参照して得た情報は、一発成功でもClaudeの既存知識とは見なさない。条件1または条件2を満たせば通過対象（カテゴリ9の詳細は後述）

**不通過時の案内**: 条件1・2を満たさないがプロジェクト内で再発しうる知見は、`/kaizen-update-docs` で `docs/LEARNINGS.md` への記録を推奨する旨をユーザーに案内する。

## 抽出カテゴリ（9カテゴリ）

以下の観点で漏れなく確認すること:

### 1. 失敗パターンと成功アプローチの対比

- 試行錯誤が発生した箇所を特定（例: ツール仕様の勘違い、API/CLIの誤用）
- 失敗したアプローチと最終的に成功したアプローチを明確に対比
- 「次回は一度目から成功する」ためのガイドラインとして記録

### 2. 暗黙のルールの明文化

- ユーザーが修正指示を出した箇所を特定
- 修正指示の背景にある「期待される動作」「暗黙のルール」を抽出
- 明文化されていなかったルールをknowledge/に追加し、次回から自動的に従えるようにする

### 3. 技術的な誤解・勘違い

- ツールやサービスの仕様誤解、パラメータの誤用
- コマンド実行の失敗とその原因
- 正しい理解・正しい使い方を記録

### 4. 情報探索の非効率の検出

- 検索を複数回やり直した、間違った候補を提示した、ユーザーに正解を教えてもらった箇所を特定
- 「探すのに苦労した」= knowledge/の該当領域に情報が不足しているシグナル
- 不足していた情報を適切なknowledge/ファイルに追加

### 5. 新規ドメイン知識

- 新しく扱った技術・ツール・サービスの概要
- 公式ドキュメント・リファレンスの参照先
- 適切なknowledge/ファイルへの追加を検討

### 6. 業務・プロジェクト横断パターン

- 複数プロジェクトに共通するパターンや手法
- 再利用可能なアプローチや設計判断
- 汎用化してknowledge/に追加

### 7. 判断の失敗

- 論理的には正しいが、考慮不足で現実的に間違った結論・設計判断を出した箇所を特定
- 見落とした観点（前提条件の未確認、エッジケース、実運用パターン等）と、正しい判断に至るために必要だったチェックを記録
- カテゴリ3との違い: カテゴリ3は「技術的に間違い」（API仕様の勘違い等）。本カテゴリは「技術的には動くが、判断・解釈が間違い」

### 8. 既存知見の精度改善

- **トリガー**: knowledge/やSkillの既存セクションを参照して作業したが、説明が不足していた・不正確だった・手順に追加ステップが必要だった
- **抽出内容**: 既存セクションの具体的な改善点（何が不足/不正確で、どう修正すべきか）
- **反映先**: 該当するknowledge/ファイルの既存セクションを更新（skills/は静的のため対象外）
- **他カテゴリとの違い**: カテゴリ1-7は新規知見の追加。本カテゴリは既存知見の品質向上（書き直し・補足・修正）

### 9. 外部調査で得た知識の還元（Query Filing Back）

- **トリガー**: セッション中に WebFetch / WebSearch / MCP（context7、AWS Documentation 等）/ その他の外部ソースを参照して情報を得た（失敗の有無を問わない）
- **抽出内容**: 外部調査で得られた知識のうち、knowledge/に記載があれば次回以降の外部調査が不要になるもの
- **反映先**: 該当するknowledge/ファイル
- **カテゴリ4との違い**: カテゴリ4は「探索の失敗・非効率」がシグナル。本カテゴリは「外部調査の実施」自体がシグナル。一発で見つかった場合も対象
- **一般化テストとの関係**: 条件3（失敗）を要求しない。ただし条件1または条件2は満たす必要がある（再利用価値が明確であること）
- **除外条件との関係**: Claudeの既存知識ではなく外部ソースから得た情報であるため、「一発成功＝既存知識で十分」の除外条件は適用されない

## データ主張を含む知見の粒度分離

数値比較・クエリ結果差異・集計値の不一致を根拠とする知見は、事実情報を以下の粒度で分離して reflector/verifier に渡すこと。未検証の派生主張を「事実」として渡すと、verifier はそれを前提に判定するため独立検証が成立しない。

- **Raw measurements（生観測）**: 「クエリAは504を返した」「CSVには9,576が記載」等、単独で観測された事実
- **Derived claims（派生主張）**: 「真値は◯◯」「片側が過小/過大」「倍率がNXに達する」等、比較・推論を経た結論

派生主張は reflector またはメインエージェント側で**反対方向の検証を1つ以上実施**してから verifier に渡す。例: 「A側が過小」仮説なら「B側が過大ではないか」の確認として JOIN 重複要因の切り分け等を行う。

## 昇格済み知見の誤認発覚時の修正フロー

knowledge/ へ昇格後の知見が誤りと判明した場合、以下の手順で訂正する（放置すると他プロジェクトで誤情報として参照される）。

1. **影響範囲の特定**: `grep -rn "該当キーワード" <knowledge_dir> .claude/skills/` で昇格先と派生参照を列挙
2. **訂正方針の選択**:
   - (a) **全削除**: 当該記述が完全な誤認で、保持すべき正しい知見がない場合
   - (b) **訂正して残す**: 記述の方向性は正しいが詳細が誤っている場合（誤った因果帰属を正しい因果に書き換える等）
   - (c) **反対方向の教訓に転換**: 誤認そのものから学ぶべき教訓がある場合（例: 誤ったL5 → L5訂正 + L6「自分のクエリを疑う」）
3. **プロジェクト `docs/LEARNINGS.md` の記録**: 訂正の経緯を「訂正版」として明示的に残す（単なる上書きではなく、誤認の痕跡を残して再発防止）
4. **knowledge/側の記述更新**: 同じ記述粒度で訂正。`**最終更新**:` 行があれば日付更新
5. **コミットメッセージ**: `fix(knowledge):` または `docs(knowledge): ... を訂正` と明示し、訂正であることを履歴に残す
6. **誤認の原因自体を教訓化**: reflect-learning プロセス自体の改善余地として本コマンドや関連skillへの反映候補を検討（例: 上記「データ主張の粒度分離」節は誤認事例から追加された）

**禁止**: 誤りを静かに削除して履歴を消すこと。訂正の経緯は将来の同種ミス防止に必要。

## ファイル反映のルール

**反映先はknowledge/のみ**: skills/は静的ファイルであり、reflect-learningの対象外。

1. **既存ファイルへの追記を優先**: 該当する領域のknowledge/ファイルに追記
2. **新規ファイル作成は最後の手段**: 既存ファイルで対応できない領域の知見であることが明確な場合のみ
3. **プロジェクト固有情報は追加しない**: knowledge/はプロジェクト横断。プロジェクト固有の教訓は `/kaizen-update-docs` で `docs/LEARNINGS.md` に記載

**knowledge/の検索方法**:
- knowledge/はシンボリックリンクであり、Glob ツールはシンボリンク先を辿れない
- ファイル読み取り・存在確認には Read ツールで直接パスを指定すること
- ファイル検索には Grep ツールを使用すること（Glob は不可）

## 簡潔性の原則

- 箇条書き優先、長文説明は避ける
- 例示は最小限（1例のみ）
- コード例は25行以内
- 重複排除、既存内容と統合
- ファイルサイズ管理（800行以内）を遵守

```
/kaizen-reflect-learning
```

## knowledge/ の自動コミット

knowledge/ への反映完了後、以下を実行する:

1. `$KAIZEN_KNOWLEDGE_DIR` が git リポジトリかどうか確認:
   ```bash
   git -C "$KAIZEN_KNOWLEDGE_DIR" rev-parse --is-inside-work-tree
   ```
2. git リポジトリの場合、未コミットの変更があれば自動コミット:
   ```bash
   git -C "$KAIZEN_KNOWLEDGE_DIR" add -A
   git -C "$KAIZEN_KNOWLEDGE_DIR" commit -m "kaizen reflect: <知見の要約（1行、英語）>"
   ```
3. git リポジトリでない場合はスキップ（警告不要）
4. コミットに失敗した場合、警告を表示して続行（knowledge/ の変更自体は保持）

# Suggest next steps

作業が一段落した時点で、蓄積されたコンテキストを**深く分析**し、次に実施すべき作業を提案する。

**動作**: 提案のみ（実行はユーザーが手動で行う）

**価値**: 形式的なチェックだけでなく、**着手価値のある発展的なアクション**（codify 候補 — 未言語化の気づき or 今セッションで機が熟した既知項目）と、**根拠付きの投機的アイデアを記録せず毎回供給する**（非永続）の2トラックを提案する

**言語**: ユーザーの言語に合わせて応答すること

---

## 実行手順

### Step 1: コンテキスト収集

以下のソースから情報を収集:

| ソース | 用途 | 必須/任意 |
|--------|------|----------|
| **当該セッションの会話履歴** | 直近の作業内容・議論・決定事項 | 必須 |
| `CLAUDE.md` | プロジェクト設定と制約 | 必須 |
| `docs/PROJECT_SUMMARY.md` | プロジェクトスコープ・目的、`§ Design Decisions`（意思決定・棄却理由） | 任意 |
| `docs/LEARNINGS.md` | 過去の失敗・制約・落とし穴 | 任意 |
| `docs/NEXT_STEPS.md` | 明示的な次ステップ・先送り条件（存在する場合。再提案の防止に使用） | 任意 |
| `knowledge/` | 蓄積済みの知識・ガイドライン | 任意 |
| `knowledge/projects/INDEX.md` | 同一レジストリ内の他プロジェクト一覧 | 任意 |
| `knowledge/projects/details/*.md` | 他プロジェクトの概要全文（横展開の検討に使用） | 任意 |
| 最近更新されたファイル | 作業中の領域特定 | 任意 |

**注意**: `knowledge/` はシンボリンクであり、Glob ツールはシンボリンク先を辿れない。Read ツールで直接パスを指定して読むこと。

**再提案ガードの根拠ソース**: 「棄却・先送り済み」の判定（Step 2.5）には、会話履歴・`docs/PROJECT_SUMMARY.md § Design Decisions`・`docs/LEARNINGS.md`・（存在すれば）`docs/NEXT_STEPS.md` を持続的記録として参照する。

**他プロジェクト参照の手順**: まず `knowledge/projects/INDEX.md` を読み、現在のプロジェクト以外の ID を特定する。次に `knowledge/projects/details/{id}.md` を読み込む。details/ が存在しない場合はスキップする。

### Step 2: 作業内容の深い理解

会話履歴から以下を特定:

| 分析項目 | 質問 |
|---------|------|
| **何を作成/変更したか** | ファイル、機能、設定等 |
| **その目的は何か** | 解決したかった課題、達成したかったゴール |
| **作業の完成度** | 完了、一部完了、プロトタイプ段階 |

### Step 2.5: 既存規約との整合性チェック（必須）

新規ルール / 規約 / 運用パターンを提案する候補が出た場合、提案前に必ず関連スキル / knowledge / 既決事項を grep して整合させる。

**スコープ**: 本チェックは **codify-track（Step 3.1 A. 発展的なアクション）限定**。投機的アイデア（3.1 B）は却下前提で永続化しないため grep 免除し、ユーザーが昇格させた時点で初めて本チェックに乗せる。

#### 手順

1. 提案候補のトピックからキーワード抽出（例:「INDEX の逆引き登録」→ `["INDEX", "逆引き"]`）
2. 関連スキル / knowledge / 既決事項を検索:
   ```bash
   grep -rln "<keyword>" .claude/skills/ docs/ 2>/dev/null
   ```
   `knowledge/` はシンボリンクのため bash の `grep -r` は黙って取りこぼす。**Grep ツール**で `knowledge/` を別途検索すること。
3. hit したファイルの該当節を読み、既存規約・過去の判断を確認
4. 結果に応じた処理:

   | 結果 | 処理 |
   |---|---|
   | **既存規約あり（完全一致）** | 新規提案を取りやめ、既存規約への参照リンクを提案に含める |
   | **既存規約あり（部分一致 / 補強価値あり）** | 既存規約を踏まえた修正案として再構成、既存規約への参照を明記 |
   | **棄却・先送り済み**（会話履歴 / `docs/LEARNINGS.md` / `docs/PROJECT_SUMMARY.md § Design Decisions` / 任意の `docs/NEXT_STEPS.md` に記録あり） | 再提案しない。覆す新事実がある場合のみ、元の棄却理由・先送り条件に言及した上で提示 |
   | **既存規約・既決なし** | 通常通り新規ルールとして提案 |

由来: 既存規約と重複する新規ルール提案や、一度棄却・先送りしたアイデアの再提示はノイズになり提案の信頼性を損なうため、提案生成前に必ず照合する。

### Step 3: 提案ロジックの適用

**3つのレベル**で提案を生成する（上位ほど価値が高い）:

#### 3.1 提案の生成 ― 2トラック（最重要）

提案は性質の異なる**2トラック**に分けて生成する。判定軸はどちらも「**堆積するか**」:

| トラック | 規範 | 記録 | 理由 |
|---|---|---|---|
| **A. 発展的なアクション**（codify） | 門は session-relevance（未言語化の気づき / 機熟既知 / 無ければ「なし」） | 採用されたら NEXT_STEPS へ | 製造→堆積が有害 |
| **B. 投機的アイデア**（speculation） | 最低1件ノルマ（本気の賭け・各案に根拠／弱い案のみ大穴ラベル） | **どこにも記録しない・毎回再生成** | 本気の賭けを供給（記録しないので採否は気軽・拾えば昇格） |

##### A. 発展的なアクション（codify-track）

以下の観点で**着手価値のある発展的なアクション**を提案（門は下記「選定ルール」）:

| 観点 | 質問 | 例 |
|------|------|-----|
| **改善** | この成果物をより良くするには？ | 機能追加、精度向上、使いやすさ改善 |
| **発展** | 関連して作ると相乗効果があるものは？ | 連携機能、補助ツール、関連パターン |
| **統合** | 既存の仕組みと組み合わせると？ | 他機能とのワークフロー化、既存スキルとの連携 |
| **検証** | 実際に使って確かめるべきことは？ | 別プロジェクトでの動作確認、エッジケースのテスト |
| **横展開** | 他のプロジェクトにも適用できる？ | パターンの汎用化、他プロジェクトの類似課題への適用（`details/` の他プロジェクト概要を参照） |

提案は「XXをYYに変更する」レベルまで具体化し、次のアクションとして着手できる粒度で、価値の理由を添えること。

**選定ルール**: A の判定軸は novelty ではなく「**今セッションの作業と結びついて着手価値があるか**」。novelty 供給は B トラックが担うため、A は新規性をノルマにしない。A に出せるのは次のいずれか:

- (a) 今回の作業で見えた課題・パターン・非効率から、ユーザーがまだ言語化していない改善機会
- (b) NEXT_STEPS の既存項目のうち、今セッションでゲート条件（前提解除・優先度上昇・新たに関連）が満たされ**機が熟した**もの。単なる読み上げは不可で、今セッションと結びつく理由を必ず添える（読み上げ退化を防ぐ規律）
- (c) (a)(b) いずれも無ければ「新規アイデアなし」と明示する（無理に製造する方が有害）

加えて: 直近に codify した施策が実地検証待ちの領域には、新施策の上積みを提案しない（観察を優先し、未検証の堆積を防ぐ）。

**事実確認**: 各提案について、変更対象のファイルを実際に読み、既に実装されていないことを確認してから提案に含めること。

##### B. 投機的アイデア（speculation-track）

**本気の賭け**を供給するトラック。**毎回最低1件**は必ず出す。記録しない（＝採否は気軽・外しても堆積しない）からこそ、質を落とさず本気のネタを出す:

- 各案に **一言の根拠**（どの非効率・緊張・機会に効くか）を必ず添える。根拠が書けないネタは出さない ― これが「採用する気になる」ための実体。
- **突飛・大胆でよい**（A より射程を広く取ってよい・実作業に紐づかなくてよい）。ただし埋め草にしない。constraint-driven に捻り出した中で本当に弱いものだけ「これは大穴だが」と**正直にラベル**する（例外であって基調ではない）。
- **記録しない**: 持続的記録（`docs/NEXT_STEPS.md` / `docs/PROJECT_SUMMARY.md § Design Decisions` / `docs/LEARNINGS.md`）のどこにも書かず、会話内のみ。毎回ゼロから再生成する（永続化しないので「未検証の堆積」が原理的に発生しない）。真剣みは記録ではなく**根拠と提示**で出す ― no-record は据置で安全性を担保する。
- **再発＝価値の signal**: 同じネタが毎回蘇るなら staying power の証拠で、昇格候補とみなす。
- **昇格パス**: ユーザーが拾った1件だけが NEXT_STEPS へ卒業し、以後は A と同じ gating（Step 2.5 含む）に乗る。

#### 3.2 影響範囲チェック（重要）

作業内容に応じて、**関連ファイルの更新漏れ**を検出:

| チェック対象 | 確認方法 |
|-------------|---------|
| `CLAUDE.md` | プロジェクト設定に反映すべき変更がないか |
| `docs/PROJECT_SUMMARY.md` | ステータスやTech Stackの更新が必要か |
| `knowledge/` 内の関連ファイル | INDEX.mdの参照リンク、関連ドキュメントとの整合性 |

#### 3.3 形式的チェック（最低限）

| チェック項目 | 確認方法 |
|-------------|---------|
| コミット | 変更がコミットされているか |

### Step 4: 提案を出力

以下の形式で提案を出力（**発展的なアクションを先頭に、投機的アイデアをその後に配置**）:

```markdown
## 次のステップ提案

**今回の作業**: [作業内容の要約]

---

### 発展的なアクション

1. [ ] **[アクション名]**: [具体的な内容]
   → 理由: [なぜこれが価値があるか]

2. [ ] **[アクション名]**: [具体的な内容]
   → 理由: [なぜこれが価値があるか]

---

### 投機的アイデア

- 💡 [アイデア]: [一言の根拠]
- 💡 [アイデア]: [一言の根拠]

---

### 整合性の確認

- [ ] [関連ファイル]: [必要な更新内容]

---

### 形式的な作業

- [ ] コミット

---

どの提案を実行しますか？ / 投機アイデアを昇格しますか？（番号で指定 / スキップ / 詳細を聞く）
```

---

## 発展的なアクションの生成ガイド（codify-track）

### 良い提案の特徴

- **具体的**: 「改善する」ではなく「XXをYYに変更する」
- **理由が明確**: なぜその提案が価値があるかを説明
- **実行可能**: 次のアクションとして着手できる粒度
- **気づきを与える**: ユーザーが自力では思いつかなかったもの

# reviewing-code

コードレビューを構造化し、観点の漏れを防ぐスキル。

## レビューフロー

| Phase | 内容 |
|-------|------|
| 0 | コンテキスト把握 |
| 1 | 変更の概要理解 |
| 2 | 観点別レビュー |
| 3 | 総合評価・フィードバック |

---

## Phase 0: コンテキスト把握

レビュー開始前に以下を確認する:

- [ ] 変更の目的（バグ修正/新機能/リファクタリング/パフォーマンス改善）
- [ ] 影響範囲（どの機能・画面に影響するか）
- [ ] 関連するイシュー・チケット番号

---

## Phase 1: 変更の概要理解

### 確認項目

1. **変更ファイル一覧**: 変更されたファイルを把握し、変更の全体像をつかむ
2. **変更量の妥当性**: 大きすぎるPRは分割を提案（目安: 400行以下）
3. **テストの有無**: 変更に対応するテストが追加・更新されているか

---

## Phase 2: 観点別レビュー

### 2.1 正確性

| チェック項目 | 確認内容 |
|------------|----------|
| ロジックの正確性 | 仕様通りに動作するか、エッジケースは考慮されているか |
| エラーハンドリング | 異常系の処理が適切か、ユーザーに適切なフィードバックがあるか |
| 境界値 | null/undefined/空文字列/空配列/0/負数の扱い |
| 型安全性 | 型の不一致や暗黙の型変換がないか |

### 2.2 セキュリティ

| チェック項目 | 確認内容 |
|------------|----------|
| 入力バリデーション | ユーザー入力をサーバーサイドで検証しているか |
| SQLインジェクション | パラメータ化クエリを使用しているか |
| XSS | ユーザー入力をHTMLに出力する際にエスケープしているか |
| 認証・認可 | APIエンドポイントに適切なアクセス制御があるか |
| 機密情報 | APIキー・パスワード・トークンがコードにハードコードされていないか |
| 依存パッケージ | 既知の脆弱性がある依存が追加されていないか |

> 参照: [PATTERNS.md § 1](../../knowledge/development/PATTERNS.md#1-セキュリティ)

### 2.3 パフォーマンス

| チェック項目 | 確認内容 |
|------------|----------|
| N+1クエリ | ループ内でDBクエリやAPI呼び出しをしていないか |
| 不要なデータ取得 | 必要なカラム・件数のみ取得しているか |
| メモリ使用 | 大量データを一度にメモリに載せていないか |
| 不要な再計算 | ループ内で同じ計算を繰り返していないか |

> 参照: [PATTERNS.md § 2](../../knowledge/development/PATTERNS.md#2-パフォーマンス)

### 2.4 保守性

| チェック項目 | 確認内容 |
|------------|----------|
| 命名 | 変数・関数・クラス名が意図を表しているか |
| 責務の分離 | 1つの関数/クラスが1つの責務に絞られているか |
| 重複 | 同じロジックが複数箇所にコピーされていないか |
| 複雑度 | ネストが深すぎないか（目安: 3段以下）、関数が長すぎないか |
| マジックナンバー | 意味不明な数値・文字列が定数化されているか |

### 2.5 テスト

| チェック項目 | 確認内容 |
|------------|----------|
| テストの存在 | 変更に対応するテストが書かれているか |
| テストの質 | 正常系だけでなく異常系・境界値もテストしているか |
| テストの独立性 | 他のテストに依存していないか |
| テスト名 | 何をテストしているか名前から分かるか |

> 参照: [PATTERNS.md § 4](../../knowledge/development/PATTERNS.md#4-テスト戦略)

## Phase 3: 総合評価・フィードバック

### 評価の出力形式

```markdown
## レビュー結果

### 概要
- 変更の目的: [目的]
- 影響範囲: [範囲]
- 総合評価: [Approve / Request Changes / Comment]

### 指摘事項

#### Must Fix（修正必須）
- [ ] [指摘内容と理由]

#### Should Fix（修正推奨）
- [ ] [指摘内容と理由]

#### Nit（軽微・好み）
- [ ] [指摘内容と理由]

### 良い点
- [良い実装や改善点を具体的に]
```

### フィードバックの原則

1. **指摘の重要度を明示**: Must Fix / Should Fix / Nit を区別する
2. **理由を添える**: 「なぜダメか」だけでなく「どうすればよいか」を提案
3. **良い点も伝える**: 問題の指摘だけでなく、良い実装も明示的に称賛
4. **コードに対してレビュー**: 人ではなくコードについてコメントする

---

## 禁止事項

1. **観点の省略**: Phase 2の全観点を必ず確認する（該当なしの場合もその旨を記載）
2. **根拠なしの指摘**: 「こうした方がよい」には必ず理由を添える
3. **好みの押し付け**: 動作に影響しないスタイルの違いは Nit として扱う

---

## カスタマイズのヒント

このファイルはサンプルです。自分のプロジェクトに合わせて以下をカスタマイズしてください:

- 技術スタック固有のチェック項目追加（例: React hooks のルール違反、TypeScript の any 使用）
- プロジェクトのコーディング規約との整合チェック
- アクセシビリティ（a11y）観点の追加
- i18n/l10n 観点の追加
- プロジェクト固有のアーキテクチャルール（例: レイヤー間の依存方向）

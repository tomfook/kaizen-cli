# Web開発パターン集

Web開発でよくある落とし穴と推奨パターン。

**⚠️ 重要**: プロジェクト横断の汎用ファイル（プロジェクト固有の内容は禁止）

---

## 1. セキュリティ

### 1.1 入力バリデーション

**原則**: ユーザー入力は常にサーバーサイドでバリデーションする。クライアントサイドバリデーションはUXのためであり、セキュリティ対策ではない。

**チェックリスト**:
- [ ] サーバーサイドでバリデーションしているか
- [ ] 型・長さ・範囲・フォーマットを検証しているか
- [ ] SQLクエリにはパラメータ化クエリ（プレースホルダ）を使用しているか
- [ ] HTMLに出力する値はエスケープしているか

### 1.2 認証・認可

**よくある落とし穴**:

| 問題 | 対策 |
|------|------|
| 認証（Authentication）と認可（Authorization）の混同 | 認証=「誰か」、認可=「何ができるか」を分離して設計 |
| フロントエンドのみでアクセス制御 | APIエンドポイントごとに認可チェック |
| 機密情報のフロントエンド露出 | APIキー・シークレットはサーバーサイドのみ |
| セッション管理の不備 | HTTPOnly/Secure Cookie、適切な有効期限 |

### 1.3 CORS設定

**原則**: `Access-Control-Allow-Origin: *` は開発環境以外で使わない。

```
# 本番環境: 許可するオリジンを明示的に指定
Access-Control-Allow-Origin: https://your-domain.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

## 2. パフォーマンス

### 2.1 N+1クエリ

**教訓**: ループ内でクエリを発行するとリクエスト数がN+1に膨張する

```
# ❌ N+1問題
users = get_all_users()           # 1クエリ
for user in users:
    orders = get_orders(user.id)  # Nクエリ

# ✅ 一括取得
users = get_all_users()           # 1クエリ
orders = get_orders_by_user_ids(  # 1クエリ
    [u.id for u in users]
)
```

**検出方法**: ORMのクエリログを有効にして、同一リクエスト内のクエリ数を確認。

### 2.2 不必要なデータ取得

**よくある落とし穴**:
- `SELECT *` で全カラムを取得（必要なカラムのみ指定する）
- ページネーションなしの全件取得
- フロントエンドで使わないデータをAPIが返す

### 2.3 キャッシュ戦略

**判断基準**:

| データの性質 | キャッシュ戦略 |
|------------|--------------|
| 静的アセット（JS/CSS/画像） | 長期キャッシュ + ファイル名ハッシュ |
| ユーザー固有データ | キャッシュなし or 短期間（private） |
| 共有参照データ（マスタ等） | 中期キャッシュ + 更新時invalidate |
| API レスポンス | ETag / Last-Modified で条件付きリクエスト |

## 3. エラーハンドリング

### 3.1 API境界のエラー設計

**原則**: エラーレスポンスの形式を統一する

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "メールアドレスの形式が正しくありません",
    "details": [
      { "field": "email", "message": "有効なメールアドレスを入力してください" }
    ]
  }
}
```

**ステータスコードの使い分け**:

| コード | 使い方 |
|-------|--------|
| 400 | バリデーションエラー（クライアント側の入力ミス） |
| 401 | 未認証（ログインが必要） |
| 403 | 認可エラー（権限不足） |
| 404 | リソースが存在しない |
| 409 | 競合（楽観的ロック失敗等） |
| 422 | 入力は正しいが処理できない（ビジネスロジックエラー） |
| 500 | サーバー内部エラー（詳細をクライアントに返さない） |

### 3.2 非同期処理のエラー

**よくある落とし穴**:
- `catch` なしの Promise / async-await
- エラー時のリトライ無限ループ
- タイムアウト未設定の外部API呼び出し

**対策**:
- 非同期処理には必ずエラーハンドリングを設定
- リトライは最大回数と exponential backoff を設定
- 外部API呼び出しにはタイムアウトを設定

## 4. テスト戦略

### 4.1 テストピラミッド

| レベル | 対象 | 特徴 |
|-------|------|------|
| Unit | 関数・メソッド | 高速、多数、外部依存なし |
| Integration | API・DB連携 | 中速、実際の依存関係を使用 |
| E2E | ユーザーフロー | 低速、少数、壊れやすい |

**原則**: Unit > Integration > E2E の比率で書く。E2Eはクリティカルパスのみ。

### 4.2 テストの落とし穴

| 問題 | 対策 |
|------|------|
| 実装の詳細をテスト | 振る舞い（入力→出力）をテスト |
| テスト間の依存・順序 | 各テストが独立して実行可能に |
| 外部サービスへの依存 | Unit: モック、Integration: テスト用インスタンス |
| 網羅率だけを追求 | 境界値とエッジケースを優先 |

## 5. API設計

### 5.1 RESTful 慣習

| 操作 | メソッド | パス例 | 説明 |
|------|---------|--------|------|
| 一覧取得 | GET | /users | フィルタ・ページネーション対応 |
| 詳細取得 | GET | /users/:id | 単一リソース |
| 作成 | POST | /users | リクエストボディにデータ |
| 更新 | PUT/PATCH | /users/:id | PUT=全体置換、PATCH=部分更新 |
| 削除 | DELETE | /users/:id | 冪等であること |

### 5.2 ページネーション

**オフセットベース**（シンプル、ページジャンプ可能）:
```
GET /users?page=2&per_page=20
```

**カーソルベース**（大量データ、リアルタイム更新に強い）:
```
GET /users?cursor=abc123&limit=20
```

**判断基準**: データ量が少なく順序が安定 → オフセット。データ量が多いまたはリアルタイム更新あり → カーソル。

# Kaizen-CLI のコンセプト

## 課題: 知識の断絶

Claude Code は強力なAI開発ツールですが、構造的な制約があります。

- **セッション間**: セッションが終わると会話コンテキストが失われる
- **プロジェクト間**: あるプロジェクトで学んだことが別のプロジェクトに引き継がれない

大規模な長期プロジェクトであれば、CLAUDE.md やプロジェクトドキュメントに知識を蓄積できます。しかし、小規模プロジェクトを多数並行する業務では、この問題が顕著になります。

具体的には以下が繰り返されます:

- **同じ説明**: 業界の専門知識や技術的な前提を毎回説明する
- **同じ手戻り**: 過去に踏んだ落とし穴を再び踏む
- **同じ調査**: 以前調べた仕様を改めて調べ直す

しかし「書き残せばいい」は解決策になりません。知識ベースを別途メンテナンスするのは余計な作業に感じられます — そして余計な作業は続きません。

Kaizen-CLI はこの問題を、別のプロセスを追加するのではなく、**実務の中に知識蓄積のループを埋め込む**ことで解決します。

---

## 着想: 引っかかりを材料にする

改善の材料を別に用意する必要はありません。それは実務の中にすでにあります — 作業中に遭遇する**引っかかり**がそれです。

- 想定外のエラー → 記録すべき落とし穴
- 調べ直した技法 → 不足していた知識
- うまくいったパターン → 再利用できるアプローチ
- ユーザーが修正した箇所 → 暗黙のルールの明文化

これらは「改善項目」としてバックログに積むものではありません。作業の自然な副産物です。Kaizen-CLI はこれらを捉えて知識ベースにフィードバックします。次に同じ状況に遭遇したとき — どのプロジェクトであっても — その知識はすでにそこにあります。

**作業と改善は、別々の活動ではない。一つだ。**

## Kaizenサイクル

サイクルは実務を包み込む形で回ります。「サイクルを回す」のではなく、実務をこなす中で学びが捉えられます。

唯一必須なのは **Execute（= あなたの実務）** だけです。Suggest、Reflect、Update Docs は任意のステップであり、やることが決まっていれば直接作業を始められます。

```
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌──────────┐
│  Init   │───▶│ Suggest │───▶│ Execute │───▶│ Reflect │───▶│ Update   │
│         │    │  Next   │    │(= あなた│    │         │    │  Docs    │
│/kaizen  │    │/kaizen  │    │  の実務)│    │/kaizen  │    │/kaizen   │
│-init    │    │-suggest │    │         │    │-reflect │    │-update   │
│-project │    │-next    │    │         │    │-learning│    │-docs     │
└─────────┘    └─────────┘    └─────────┘    └─────────┘    └──────────┘
                    ▲                                              │
                    │   実務中の引っかかりが knowledge/ を育て      │
                    │       次のサイクルを加速させる                 │
                    └──────────────────────────────────────────────┘
```

### Init — プロジェクトの初期化

**一度だけ実行**。新しいプロジェクトでKaizen-CLIを使い始めるときに `/kaizen-init-project` を実行します。

- `knowledge/` のsymlinkを作成（共有ナレッジベースへの接続）
- `CLAUDE.md` と `docs/PROJECT_SUMMARY.md` を生成
- プロジェクトレジストリに登録

これにより、過去のプロジェクトで蓄積された知識がすぐに利用可能になります。

プロジェクトをレジストリから削除するには `/kaizen-unregister-project` を実行します。レジストリのエントリのみが削除され、symlinkやプロジェクトファイルには影響しません。

### Suggest — 次のアクションの提案

作業が一段落したとき、または次に何をすべきか迷ったときに `/kaizen-suggest-next` を実行します。

- 今回の作業内容を深く分析
- **ユーザーが気づいていない発展的なアクション**を提案
- 関連ファイルの更新漏れを検出

単なるTODOリストではなく、蓄積された知識とプロジェクトコンテキストを踏まえた提案を行います。

### Execute — 実行（= あなたの実務）

**ここはあなたの普段の仕事そのものです**。機能の実装、バグ修正、データ分析、コードの記述 — あなたがやることは変わりません。変わるのは、過去の経験が味方についていることです。

- 蓄積された knowledge/ を参照しながら作業。サイクルを重ねるほど、過去に踏んだ落とし穴・調べ直した技法・暗黙のルールが既に揃った状態で作業を始められます
- skills/ が特定のタスクパターンを検知すると自動発動してガードレールを提供

### Reflect — 引っかかりが知識に変わる

作業が一段落ついたときに `/kaizen-reflect-learning` を実行します。作業中に生じた引っかかりを分析し、knowledge/ に反映します。

- 失敗パターンと成功アプローチの対比
- 暗黙のルールの明文化
- 技術的な誤解の記録と訂正
- 情報探索の非効率から知識の不足を検出

重要なルール: **セッション中に失敗・リトライが発生した情報は無条件で採用されます**。「記録に値するか」を判断する必要はありません — 引っかかりが生じた事実が、それだけで十分な理由です。

反映された知識は symlink を通じて、すべてのプロジェクトで即座に利用可能になります。

### Update Docs — プロジェクトドキュメントとレジストリの同期

reflect-learning の後に `/kaizen-update-docs` を実行し、プロジェクト側のドキュメントを最新化します。

- 作業中の変更に基づいて CLAUDE.md と docs/ を更新
- PROJECT_SUMMARY.md をプロジェクトレジストリ（`knowledge/projects/INDEX.md`）と同期

これにより、将来のセッションや他プロジェクトからの `/kaizen-suggest-next` でプロジェクトの文脈が正確に参照されます。

## 知識のライフサイクル: 蓄積と整理

上のサイクルは**短期ループ** — 日々の実務のリズムを捉えています。しかし知識にはもっと長い時間軸があります。蓄積だけを続ければ、`knowledge/` はやがて歪みます: エントリが重複し、仕様が陳腐化し、ノイズがシグナルを埋もれさせる。複利効果にはライフサイクルの両輪が必要です。

- **Reflect** は蓄積する。セッションごとの引っかかりが知識になる。
- **Audit** は整理する。定期的に `/kaizen-audit-knowledge` が冗長・SSOT違反・陳腐化をスキャンし、削減候補を提示してユーザーの承認を仰ぐ。

Audit が日々のサイクルの外側にあるのは意図的です。時間軸が異なる — セッションごとではなく、週単位・月単位でまわる — からで、判断に必要な観点は知識がある程度落ち着いてから初めて見えてくるものだからです。

Audit の判定を支える2つの原則は、いずれも直感に反します。

**親しみよりも運用可能性**。「知っていること」と「確実に運用できること」は別物です。Claude がリマインドなしで確実に運用できる知識は削減候補になります — 場所を取るだけで挙動を変えないからです。一方、広く知られていても間違えやすい知識は残します。問うべきは「これは一般的か」ではなく「消したら結果が悪化するか」です。

**失敗由来の知識は守る**。実際の失敗や事故から生まれたエントリは、自明に見えるという理由で削除することはありません。一般論に見える助言も、実は痛い目を見て得たものであれば、純粋な推論では再現できない文脈を背負っています。Audit は教科書的な知識と、傷跡として残った知識を区別し、後者を保護します。

軽量な**鮮度シグナル**(90日以内 / 90日超 / 180日超)は、どのファイルを重点的に見るかの優先順位付けに使います。重要な点として、鮮度が低いこと自体は削除理由になりません — 命名規則や用語は何年も有効であり続けます。鮮度は注意の焦点を絞るためのものであり、行動を決めるものではありません。

Reflect と Audit の両輪が揃って初めて、`knowledge/` は単に膨らむアーカイブではなく高シグナルのリソースとして育ちます。後述する複利効果は、両輪が機能してこそ実現します。

## 知識の3つの層

作業を通じて蓄積される知識は、自然と3つのカテゴリに分かれます — そしてこれらを混在させると問題が生じます。

**プロジェクト横断の知識**は、特定のプロジェクトを超えて価値を持ちます。APIの落とし穴、ドメインの専門知識、ツールの癖、コーディングパターン、暗黙のルールは、どこでも役立つものです。一度学んだことは、二度と学び直す必要がないはずです。

**プロジェクト固有の教訓**は、プロジェクトの開発中に発見された失敗、制約、落とし穴です。「このAPIのレート制限は100回/分」「CSVエクスポートはUnicode文字で壊れる」— これらはこのプロジェクトの文脈で得られた貴重な発見です。やがて横断知識に一般化されるものもあれば、ここでのみ有効なものもあります。

**プロジェクトドキュメント**は、プロジェクトが何であり、どう動くかを記述します。アーキテクチャの決定、技術スタックの選択、命名規則、ロードマップ、設計の理由付けは、プロジェクトに関する事実であり、摩擦から学んだ教訓ではありません。

| 層 | 配置場所 | 例 | 更新コマンド |
|----|---------|---|------------|
| **プロジェクト横断知識** | `knowledge/`（共有） | ドメイン専門知識、再利用可能なパターン、暗黙のルール | `/kaizen-reflect-learning` |
| **プロジェクト固有教訓** | `docs/LEARNINGS.md` | 失敗、制約、落とし穴 | `/kaizen-update-docs` |
| **プロジェクトドキュメント** | `CLAUDE.md`, `docs/` | アーキテクチャ、設定、ロードマップ、チーム規約 | `/kaizen-update-docs` |

Kaizen-CLI はこの3つの層を明確に分離します。

プロジェクト横断の知識は共有 `knowledge/` ディレクトリに蓄積され、すべてのプロジェクトにsymlinkされます。reflect-learning がどのプロジェクトで再利用可能な知見を捉えても、手動コピーや同期なしに、他のすべてのプロジェクトで即座に利用可能になります。プロジェクト固有の教訓は `docs/LEARNINGS.md` に蓄積され、何がうまくいかなかったか、何に注意すべきかの記憶として機能します。プロジェクトドキュメントは `CLAUDE.md` と `docs/` に留まり、プロジェクト自体を記述します。

判断ルールはシンプルです:
- **プロジェクト名を取り除いても意味が通る知見** → `knowledge/`
- **このプロジェクト固有の失敗・制約・落とし穴** → `docs/LEARNINGS.md`
- **プロジェクト自体の事実情報** → `CLAUDE.md` または `docs/`

教訓にはライフサイクルがあります: 一般パターンは reflect-learning を通じて `knowledge/` に**卒業**し、解消済みの制約は削除され、設計に反映済みの教訓は引退します。これにより無限の蓄積を防ぎ、各エントリが実用的であり続けます。

この分離こそが、Kaizen-CLI を単なるプロジェクト単位のツールからプロジェクト横断の知識プラットフォームに変えるものです。これがなければ、すべての知識をローカルに留める（複利効果を失う）か、すべてを共有スペースに放り込む（ノイズが増えて有用性が低下する）かのどちらかになってしまいます。

### Auto Memory の位置づけ

Claude Code の auto memory（`~/.claude/projects/`）は、この3層の下に位置する低コストなメモ領域です。個人の好み、一時的なコンテキスト、単発のメモなどを記録します。バージョン管理されず、プロジェクト間で共有されず、人間がレビューすることもありません。

以下のいずれかに該当する情報は、memoryから適切な層に昇格すべきです:
- **復元コスト** — 失われたら再構築に手間がかかる
- **読者の存在** — チームメンバーや未来の自分が参照する可能性がある
- **意思決定の根拠** — 「なぜそうしたか」の追跡が必要

`/kaizen-update-docs` がmemoryファイルを定期的に棚卸しし、永続化すべき情報を `docs/` や `knowledge/` にルーティングし、陳腐化したエントリを整理します。これにより、価値ある観察がバージョン管理されないマシンローカルなストアに閉じ込められることを防ぎます。

## なぜ使うほど速くなるのか

### 知識蓄積のメカニズム

```
プロジェクトA（個人）          プロジェクトB（仕事）       プロジェクトC（仕事）
┌────────────┐             ┌────────────┐           ┌────────────┐
│ CLAUDE.md  │             │ CLAUDE.md  │           │ CLAUDE.md  │
│ docs/      │             │ docs/      │           │ docs/      │
│            │             │            │           │            │
│ knowledge/ ─┐            │ knowledge/ ─┐          │ knowledge/ ─┐
└────────────┘ │            └────────────┘ │          └────────────┘ │
               │                           │                         │
               ▼                           ▼                         ▼
  ┌──────────────────┐      ┌──────────────────────────────────────┐
  │ default registry │      │ work registry                        │
  │                  │      │                                      │
  │ meta/            │      │ meta/                                │
  │ projects/        │      │ projects/                            │
  │ (domain files)   │      │ (domain files)                      │
  └──────────────────┘      └──────────────────────────────────────┘
  └───────────────────── $KAIZEN_KNOWLEDGE_DIR ────────────────────┘
```

ポイント:

1. **プロジェクト固有の情報**（CLAUDE.md、docs/、LEARNINGS.md）と**横断的な知識**（knowledge/）が分離されています — 上述の「知識の3つの層」モデルの通りです
2. knowledge/ は symlink で同じレジストリ内の全プロジェクトから同じ実体を参照します
3. reflect-learning で知識が蓄積されるたびに、そのレジストリ内のすべてのプロジェクトで即座に利用可能になります
4. **レジストリで文脈ごとに知識を分離** — 職場の知識と個人の知識が混ざらない。各レジストリが独立した meta/、projects/、ドメインファイルを持つ

### 蓄積される知識の例

| カテゴリ | 例 | 効果 |
|---------|---|------|
| **失敗からの予防線** | 「このAPIは第2引数がnullだとサイレントに失敗する」 | 同じ落とし穴を二度と踏まない |
| **業界の専門知識** | ドメイン用語の定義、業務ルール | 毎回の説明が不要になる |
| **技術的な知見** | ツールの癖、ベストプラクティス | 調査時間の短縮 |
| **暗黙のルール** | コーディング規約、命名慣例 | 手戻りの削減 |

### 複利効果

知識の蓄積は**複利的**に効果を発揮します。

- **1サイクル目**: 知識ゼロからスタート。調査・試行錯誤が多い
- **5サイクル目**: 基本的な落とし穴は記録済み。作業がスムーズに
- **20サイクル目**: ドメイン知識が充実。Claude Code がまるでチームメンバーのように動く

従来の「毎回リセット」される開発と異なり、**過去の自分の経験がすべて引き継がれる**開発体験が得られます。

## 知識の層構造

Kaizen-CLI は知識を3つの層に分けて管理します。

| 層 | 配置場所 | 性質 | 変更タイミング |
|---|---|---|---|
| **参照知識** | `knowledge/` | ドメイン知識、パターン、ガイドライン | reflect-learning で蓄積 |
| **手続き知識** | `skills/` | 特定タスクのステップバイステップ手順 | 静的（ユーザーが手動で作成・更新） |
| **操作** | `commands/` | ワークフローのトリガー | 静的（Kaizen-CLI が提供） |

重要な設計判断: **reflect-learning が蓄積するのは knowledge/ のみ**。skills/ は静的なファイルであり、自動的に変更されることはありません。これにより、スキルの動作が予測可能に保たれます。

## 対象ユーザー

### 向いている人

- **小規模プロジェクトを多数並行する開発者・アナリスト**
  - プロジェクト間で知識が断絶し、同じ作業を繰り返している
  - 例: フリーランス、データアナリスト、社内ツール開発者

- **特定ドメインで繰り返し作業する人**
  - 業界特有の知識やツールの癖が蓄積されると効果が大きい
  - 例: AWS開発、データ分析、Web開発

- **Claude Code をもっと活用したい人**
  - CLAUDE.md は使っているが、プロジェクトを超えた知識管理ができていない

### 向いていない人

- **単一の大規模プロジェクトのみに従事している人**
  - プロジェクト内のCLAUDE.md とドキュメントで十分
  - 横断的な知識共有の恩恵が小さい

- **Claude Code を使っていない人**
  - Kaizen-CLI は Claude Code の skills/commands 機能に依存している

## 従来のアプローチとの比較

| 観点 | CLAUDE.md のみ | Kaizen-CLI |
|------|---------------|------------|
| 知識の範囲 | プロジェクト内 | プロジェクト横断 |
| 知識の蓄積 | 手動で記述 | reflect-learning で半自動 |
| 次のアクション | 自分で考える | suggest-next が提案 |
| 新プロジェクト開始時 | ゼロから | 過去の知識を即座に利用 |
| 知識の形式 | 自由記述 | 構造化（INDEX逆引き、800行ルール） |

Kaizen-CLI は CLAUDE.md を**置き換える**ものではありません。CLAUDE.md（プロジェクト固有）と knowledge/（プロジェクト横断）を**組み合わせる**ことで、知識管理を強化します。

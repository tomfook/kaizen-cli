### 社内版からの機能移植時のチェックポイント

社内版から改善を持ち込む際に毎回繰り返し発生する判断:

- **除外**: 社内固有のドメイン情報、社内のリポジトリ・ストレージ運用、業務種別固有テンプレート
- **保留**: OSS版で前提が揃っていない機能（社内版のように中央集約された前提構造が必要なものは、まず OSS版で対応するレジストリ構造を整備してから移植する）
- **置換**: prefix（社内版の prefix → `kaizen-`）、`context/` → `knowledge/`、環境変数（共有リポジトリを指す社内版の変数 → `KAIZEN_KNOWLEDGE_DIR`）、skill参照、`git` コマンドの前提
- **レジストリ構造差分の補完**: 社内版は種別ごとのディレクトリに各プロジェクト固有ファイルが中央集約されているが、OSS版のレジストリは `projects/details/` のみ（PROJECT_SUMMARY コピー）で他の集約ツリーは持たない。中央集約を前提とする機能を移植する際は、対応する集約ツリー（例: `projects/learnings/`）を新設し、`kaizen-update-docs` の Step 5 に sync サブステップを追加するパターンで補完する
- **bilingual 対応**: 社内版は JA 単一だが OSS版はテンプレート/ドキュメントが EN/JA 両対応のため、grep パターンや出力は両言語を考慮する（例: `**最終更新**:` と `**Last updated**:` を両方検出する）。置き換えた語が残っていないかの検査も、両方の表記で行う（#47 では、日本語の語だけで組んだ最初の検査が、英語版に残った旧い節名と旧い承認表記を拾えなかった）
- **規約は社内版での適用対象を確かめてから移す** (2026-11-24): 「1 ファイル 800 行」は社内版では知識ファイル向けの目安で、スクリプトには掛かっていなかった。公開版の `CLAUDE.md` の文言を広く読んで lint と tracking issue に載せ、参照チェッカの移植で分割を迫られてから改定した（Markdown 800 行／スクリプト 1,500 行目安）
- **抽出・照合系の道具は、公開版の実物に当ててから受理書式を決める** (2026-11-24): 社内版の抽出規則のままでは、公開版の昇格先マーカー（バッククォートなしの `→` 形）とアンカー付きリンクを 1 件も拾えなかった。自リポジトリの `docs/` とテンプレートに `kaizen-check-refs.py --project . --list` を当て、SKIP に出る形を見てから規則を決める
- **issue が前提にした移植元の版を確かめる** (2026-11-26): issue を書いたあとも社内版は進む。#46 では、起票の 2 日後に社内版が別の設計へ切り替わっており、最新版をそのまま移植元にすると issue に無い設計変更まで持ち込むところだった。移植元ファイルの `git log` で起票日前後のコミットを見て、当時の版を `git show <rev>:<path>` で取り出して読む。新しい設計は別の issue として扱う
- **移植元の新しい設計は、公開版の制約に当てて測ってから決める** (2026-11-27, #70): 社内版が「サブエージェントがセッションの記録を読む」方式に切り替えた件で、取り込む前に 3 点を確かめた。(1) 依存する仕様が公式に保証されているか（記録の形式は公式ドキュメントに「内部仕様で、どのリリースでも壊れうる」とあった）(2) 入力が何倍になるか（同じ作業 1 回分で、ペイロード 5,827 字に対し記録の要約は 89,076 字）(3) 置き換えようとしている方式に、実際に欠落があったか（記録とペイロードの突き合わせで、失敗の欠落は 0 件、数値の食い違い 3 件、手順から外れた箇所 6 件。最後の 6 件は別エージェントの報告で、うち 5 件を記録で確認）。公開版で効いたのは (1) と、python3 が任意の依存なので旧経路を消せないことだった。全面的な切り替えは見送り、効果が確認できた部分だけを別の issue（#73）にした
- **移植元の文書が引く根拠は一次ソースで読み、試された条件が自分の規則と同じかを見る** (2026-11-27): 判定基準の置き換えの根拠にされていた報告は実在したが、試されていた規則は「失敗だけを記録する」で、公開版の「失敗は必ず採用する」とは同一ではなかった。同じ報告には、古いモデルには誘導が効いたともあった。置き換えは行ったが、モデルを固定している verifier の差し戻し規則は残した
- **移植元の運用規則が、道具の検出の弱さを補うためのものでないかを見る** (2026-11-27, #48): 社内版には「完了の記録に検出語を書かない」「記録の欄に余計な日付を書かない」という規則があった。どちらも、語の検索で候補を拾い、日付の種類数で世代を数える道具から来ていた。公開版では行頭のラベルで読む形にしたので、規則ごと移さずに済んだ。差分の起点も同じで、日付（時刻を省くと実行時刻が起点になる）をコミットに替えると、注意書きが要らなくなった

### framework/.claude/ に要素を追加したら dev リポジトリ自身の .claude/ を再同期する

kaizen-cli リポジトリは自身のコマンドをドッグフーディングするため、`.claude/` に `framework/.claude/` への symlink を持つ。`framework/.claude/{skills,commands,agents}/` に新規要素を追加しても、dev リポジトリの `.claude/` 配下の symlink は自動更新されない。古いまま放置すると `/kaizen-reflect-learning` 等のサブエージェント委譲が黙って劣化する（`.claude/agents/` 不在で reflector/verifier が見つからない等）。

- 新規 skill/command/agent の追加・改名・削除後は `bash framework/bin/kaizen-init.sh sync-links` を実行する（欠落を張り、宙吊りを外す。手で `ln -s` しない）。未同期は `/kaizen-suggest-next` の冒頭でも検出される（2026-11-23, #62）
- `.claude/` に新しいサブディレクトリ（例: `agents/`）を作る場合、`.gitignore` に `/.claude/<dir>/kaizen-*` を追加する。symlink は machine 固有の絶対パスを含むためコミットしてはならない

### Bilingual テンプレ見出しを単一ファイルから §参照する際は英語語幹を全言語で温存する (2026-06-27)

### スクリプトとテストは macOS の CI でも走る — bash 3.2 と BSD 版コマンドを前提に書く (2026-11-23)

- **状況**: `.github/workflows/test.yml` は `ubuntu-latest` と `macos-latest` の両方で `bash tests/run_all.sh` を実行する。開発端末（Linux・bash 5・gawk）で通っても macOS で落ちうる
- **制約**: `set -u` 下の空配列の展開（bash 3.2 でエラー → 改行区切りの文字列で持つ）、`grep -P`、gawk 拡張（`gensub`・`\<`）、`readlink -f`、`sed -i` の引数形式を避ける。`wc -l` の出力は先頭に空白が付く
- **CI で実際に落ちた 2 件** (2026-11-24): (1) BSD awk は、読み手がパイプを閉じる（`… | head -1`）と SIGPIPE で終わらず、書き込みエラーを出して終了コード 2 を返す。awk の非ゼロ終了をそのまま失敗扱いにしない (2) bash 3.2 は `$( … )` の中に書いた `case` 文を解釈できない（構文エラー）。関数に出して、`$( )` の中は関数呼び出しだけにする
- **awk の正規表現**: グループ内の `$`（`(x|$)` の形）は処理系で扱いが分かれうるので使わない。`a ~ /…x/ || a ~ /…$/` のように条件を 2 つに分ける
- **grep とロケール** (2026-11-27): (1) busybox の grep は、`-I` / `-a` を指定してもバイナリを除外しない（BusyBox v1.35.0 で実測: エラーにならず受け付け、NUL を含むファイルも `-lI` で一致として返す。`--help` の一覧には載っていない。当初「busybox に無い」と記憶から書いたのは誤りで、実測して訂正した）。バイナリの除外は NUL バイトの有無で自分で判定する（`tr -d '\000' < f | wc -c` とファイルサイズの比較） (2) `grep -r` が symlink を辿るかは実装で違う。再帰は `find … -exec grep … {} +` で書く (3) 文字数での切り詰めは、awk の `substr`・`cut -c`・bash の `${s:0:N}` のどれも、ロケールと実装で文字単位かバイト単位かが変わる。`LC_ALL=C` でバイトとして切り、切れ目が UTF-8 の継続バイト（128〜191）なら位置を戻す（実装: `framework/bin/kaizen-search-knowledge.sh` の `clip`）
- **手元での代替検査**: awk を mawk に、awk・grep・sed・find などを busybox 版に差し替えた PATH でテストを流すと、GNU 依存の一部を push 前に拾える（BSD 版そのものの検証にはならない）
- **bash 3.2 の手元検査** (2026-11-24): Docker の `bash:3.2` イメージで全テストを回せる（`docker run --rm -v "$PWD":"$PWD":ro -w "$PWD" bash:3.2 sh -c 'apk add --no-cache git python3 >/dev/null; bash tests/run_all.sh'`。リポジトリは同じ絶対パスにマウントする＝`.claude/` の symlink が絶対パスのため）。ツール類は busybox なので BSD 版の検証にはならない。このコンテナには `/bin/bash` が無い（bash は `/usr/local/bin/bash`）。PATH を絞って子スクリプトを起動するテストは、シバンに頼らず、先に `command -v bash` で解決した bash で起動する
- **昇格候補**: macOS の CI を持つシェルのプロジェクトすべてに当てはまる（先送り: 別のプロジェクトで、シェルスクリプトを macOS でも動かすとき）

### 配布物のコマンド定義に参照チェッカを掛けると、利用者側のファイルへの参照が MISS になる (2026-11-27)

- **状況**: `kaizen-check-refs.py --project framework` に `.claude/commands/` のファイルを渡すと、`docs/PROJECT_SUMMARY.md` の Design Decisions 節のような参照が `referenced file not found`（終了コード 1）になる。参照先は利用者のプロジェクトに置かれるファイルで、`framework/` 配下には無い
- **対処**: コマンド定義から配布物内の節（`CRITERIA.md` の節）を指す参照は、チェッカでまとめて検査しない。参照の文字列が書かれていることと、参照先の見出しが実在すること（`kaizen-extract-section.sh` の終了コード 0）を、テストで別々に確かめる（実装: `tests/test_search_knowledge.sh` の `test_call_sites`）
- エージェント定義とスキルは利用者側のファイルを節で参照していないので、チェッカをそのまま掛けられる（`tests/test_reflect_structure.sh`）

### このリポジトリの docs から、開発者の手元の knowledge/ を参照しない (2026-11-26)

- **状況**: ある教訓を自分の knowledge/ に昇格し、`docs/LEARNINGS.md` のエントリを昇格先へのポインタ（`→` と knowledge 配下のパス、`§` と見出し）に置き換えた
- **問題**: knowledge/ は開発者ごとの私有リポジトリで、公開リポジトリの読み手と CI には存在しない。`tests/test_check_refs.sh` の「このリポジトリの docs に参照切れが無い」が CI で落ちた。手元では、リポジトリ直下の `knowledge` symlink 経由で参照が解決するため、全テストが通っていた
- **教訓**: このリポジトリは配布物で、利用者のプロジェクトとは違う。docs/ から knowledge/ への昇格ポインタは書かず、公開側に残す内容は本文で持つ。手元で確かめるなら `knowledge` symlink を外した状態（または別ディレクトリへの clone）でテストを流す
